# Public program catalog and application handoff

Implemented November 23, 2026. **Programs** in the public website navigation opens `/portal/programs/`. Visitors can search published program codes/titles, page through twelve results at a time and open a program's published description, academic-year label, award/level/school/field/site context and offered majors, minors and specializations. **Back to programs** restores the search and accepted results page. Search, paging and details work without JavaScript.

## Choose what the website publishes

Academic publication and website visibility are separate decisions. Creating or publishing an academic program does not automatically publish its description on the website.

1. Open **Academic catalog → Programs → selected program → Website catalog**. The action requires `sis:catalog:manage`, `sis:portal:manage` and `sis:portal:publish` together. No new permission or automatic grant is added.
2. Choose a **Published program definition**, identified by its retained academic-year label, title and catalog revision. The chooser pages fifty genuine retained definitions at a time; earlier generated cohort rows without a complete program definition are excluded. Use **Older publications** and **Newer publications** without losing the chosen definition.
3. Enable **Show this program in the public catalog**, then **Review website catalog**. The preview uses the selected immutable description and academic options. It renders plain text, including literal angle brackets.
4. **Revise catalog settings** keeps the chosen version and visibility. **Confirm catalog publication** makes it available. The success view links to **View public program**; **Back to record** returns to the program workspace.
5. Later draft edits or academic publications leave the public selection unchanged. To update the website, choose and review another published version. To remove it, clear the visibility option and confirm removal. Hiding removes both the public card and direct detail page; it does not disable application forms, alter academic publications or change a student's curriculum.

Reviews expire after twenty minutes and bind the actor, program, selected source and current visibility revision. Role and program locks, source/history verification, required audit and final permission/source/state checks protect confirmation. Failed/stale confirmations retain the proposed settings for review; explicit **Reload catalog settings** reloads current saved state. An immediate exact accepted retry is idempotent. Once a later catalog change is saved, an old retry is stale and cannot restore an earlier public selection. Closing or losing access prevents delayed responses from reopening the drawer. No draft or private payload is stored in the browser.

The built-in home page and Vihzhuo **Live academic programs** block now show up to six opted-in program cards and link to program details. The block's heading, introduction, caption and link label remain editable through Settings. The default link label is **Explore programs**. Existing configured link text remains the theme/editor's choice. All three bundled campus themes inherit the new Programs navigation and shared native program screens. Custom navigation menus can link directly to `/portal/programs/`; their existing approval workflow remains independent.

## Continue into an application

When an application form is currently available, **Apply to this program** opens the existing application screen with the program selected, including programs beyond its initial one-hundred-option page. When no form is available, the public detail asks the visitor to contact admissions rather than presenting an unusable application action. This is current availability guidance; the application service still verifies the actual active form and permissions at submission.

After choosing an entry term, a guest's **Create your account** or **Sign in to apply** links carry only validated public program/term identities. Those selections survive account/sign-in links, failed-credential redirects and successful sign-in continuation. Already signed-in visitors retain the selected destination. Return destinations are fixed application routes: callers cannot provide an external redirect URL. Hints create no application, account, student, curriculum choice or accepted decision by themselves and grant no access.

Published [incompatible curriculum pairs](program-publication.md#incompatible-curriculum-choices) appear beside the offered academic options. These public code/title labels explain combinations that cannot be selected together; the registrar still applies the student’s own retained program policy. The website version does not decide that policy.

The existing person/account, owner checks, form publication, CSRF, original submission artifacts, admissions decisions and matriculation rules remain authoritative. Applying to a broad program does not automatically select one of its listed majors/minors. Those choices follow the institution's advising and curriculum-selection workflow. The entry term and admissions process determine the applicable academic curriculum; viewing a website catalog version does not assign it to a student.

## Storage and validation

Migration **`20261123000012_CreateSisProgramDiscovery`** adds one operational visibility row per configured program, with an optional retained publication reference/hash, optimistic revision, last command/actor references and update time. No existing program is opted in. Ordinary public lists use bounded indexed projections; detail reads validate the retained source/hash and visibility and expose only curated public fields. They do not replay person/student history or expose publication reasons, internal ownership data or raw events. Publishing verifies the chosen academic definition against its protected program stream. The sole authoritative event journal remains `sis_history_events`.

The configured MariaDB accepted migration 12 with zero new visibility rows. All twenty original protected event envelopes retain the same SHA-256 aggregate; no existing program publication or academic fact is converted. Native acceptance identified and resolved a foreign-key name collision with program-department storage before the successful retry. Five SQL compiler dialects and fictional SQLite workflows supplement this native check without certifying all live PDO drivers.

Focused checks cover explicit opt-in, pinned versions after later publications, search/paging, strict publication ownership, expired/stale proofs, immediate retry/later-withdrawal safety, source/authority/audit rollback, actual providers/CSRF/private responses, large-chooser handoff and typed continuation hints. Browser checks cover literal wording, preserved review drafts, record returns, three-theme narrow/enlarged-text layout, keyboard use, account/sign-in links and automated WCAG checks. All checks remain bounded and use fictional records. Broader institutional program eligibility, custom theme qualification and release acceptance remain separate work.
