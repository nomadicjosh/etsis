# Legacy SELECT reporting acceptance review

This review uses the actual examples in `legacy/docs/sql-query`, the saved-query/SQL routers and module, the section-roster/transfer routers, and the reporting views in the legacy migrations. The legacy feature allowed SELECT reporting across related tables; it was substantially more capable than the original fixed student-list report. Read-only access must preserve analytical power. This document is an acceptance plan, not a claim that the replacement builder is complete.

## Required reporting architecture

The [transfer completion-date extension](transfer-completion-reporting.md) now supplies current/corrected and original award completion dates in existing credit/student/application sources. Calendar summaries and whole-row latest/earliest selection share exact award/student/credit/origin joins, explicit unknowns, named copies and current permissions. No source/date is inferred from term dates or CEUs. [Institutional academic completion/source dates](institutional-academic-date-reporting.md) now have an atomic event-derived index, explicit older unknowns, one-stream operator reconciliation and dependent-report/export readiness. Ordinary reports never replay the journal.

1. Store a versioned, typed report definition with root dataset, relationship aliases, INNER/LEFT join selection, output expressions/labels, predicates, grouping, HAVING and deterministic sorting. jQuery QueryBuilder handles predicate editing; relationship, expression and grouping editors are additional controls, rather than pretending a WHERE-condition widget is the whole reporting system.
2. Expose a discoverable relationship/field registry spanning authorized domains, including student program catalog bindings. Authorize every joined or referenced dataset and field, including fields used only in filters, expressions or sorting. A report share must not grant access to the underlying academic, finance, HR, contact or private case data.
3. Compile a SELECT execution plan with bound literals and repository-owned identifiers through the supported database dialects. A read-only query is not inherently privacy-safe or resource-bounded. Keep credentials, encrypted notes/documents, raw event payloads and private communication content outside general reporting. Domain-specific read models provide legitimate reportable information instead.
4. Handle one-to-many relationships deliberately. Joining several fact tables can multiply tuition, fees or student counts. Provide aggregates at a declared grain (for example student + account + currency + term) before combining datasets, plus EXISTS/NOT EXISTS filters where row multiplication is unwanted.
5. Preserve NULL/zero distinctions, compound predicates, date ranges, aliases, selected fields, calculated columns, SUM/COUNT/MIN/MAX, DISTINCT, grouping/HAVING and latest-row patterns. Normalize RIGHT JOIN use cases by changing the root and using LEFT JOIN so institutions get equivalent results across supported databases.
6. Define stable pagination for detailed and grouped output, bounded previews and exports, configurable execution/resource limits, cancellation and actionable validation. Never silently truncate a report and present it as complete. Validate grouping explicitly; do not reproduce permissive MySQL queries that return arbitrary ungrouped columns.
7. Recheck execution and export permissions each time; retain private/no-store responses, CSRF for browser mutations, debug suppression, formula-safe exports and metadata-only audit. Shared report definitions are distinct from saved output snapshots and from permission to perform a batch action.

## Acceptance scenarios to carry forward

- A 2024 matriculant remains in the 2024 program catalog cohort after the 2025 catalog is published, and reports can select the student's assigned catalog independently of the latest published catalog.
- A section headcount report includes zero-enrollment sections and supports an institution-selected HAVING threshold; faculty and room are optional relationships.
- A student with several programs appears once in a person-grain selection, or once per assignment in an explicitly selected program-grain report.
- Two fee rows and three payment rows do not produce six-times-inflated balances; mixed currencies are never added into an unlabeled total.
- Latest registration uses institutional term chronology, not a lexical comparison of arbitrary term codes.
- A recipient of a shared academic/financial report who lacks the relevant source permissions is denied before query execution, even when protected fields appear only in a filter.
- A report may feed a reviewed registration population without changing any rows until the separate authorized batch confirmation.

The old examples also include SSN-derived PIN functions, raw SQL logging and name-based sharing. Those are not requirements to reproduce: they conflict with the current privacy and identity design. Analytical functions and joining power remain requirements; sensitive source access and operational actions need their own explicit permissions.

## Current implementation stage

Report Studio implements student/current-primary-program records plus the first three joined dataset families: student program/catalog assignments, academic credit/final-grade snapshots, and sections/enrollments. Staff can select chained INNER/LEFT relationships, calculated numeric columns, readable names/statuses, nested conditions, related-row join conditions, grouping, summary conditions, distinct output and ordering. Text/date MIN/MAX retain their types when filtering summarized output. AJAX previews pair exact-value tables with charts, with versioned encrypted saves, existing account-based sharing and formula-safe CSV exports of the current page. Source permissions are required for every reference and ancestor relationship, including filter-only paths.

The remaining acceptance work above includes more domain sources, derived financial aggregates, general latest-row selectors, configurable relationships beyond the approved registry, general expression trees and wider reviewed population hand-offs. The current UI is an initial working stage, not a full replacement for every legacy SELECT. See [backend-workspace.md](backend-workspace.md#relational-report-studio) for setup and limits.

[Saved report settings](workflow-review.md#saved-report-results-and-automatic-removal) distinguish live dynamic reports from encrypted complete static captures, with independent optional expiry. [Complete background exports](workflow-review.md#complete-report-exports) now prepare up to 25,000 rows/16 MiB, with requester-only progress, cancellation, authenticated private downloads and bounded artifact retention. Capture/export limits and deployment cleanup instructions are documented there; broader load and live multi-engine acceptance remain open.

The [latest-registration relationship and starting points](workflow-review.md#latest-registration-reports) now cover the chronological student/latest-term use case from `understanding-joins.md`, including optional unmatched students. A correlated student-indexed lookup and the existing cross-database SELECT-limit helper choose one retained term. It uses current projections, excludes cancelled/removed early-drop rows, declares all-pursuit scope and avoids lexical term-code ordering. This is a curated latest-row relationship; it does not complete a general alias or anti-join authoring interface.

[Related-record condition cards](workflow-review.md#related-record-conditions) now support scoped `EXISTS`/`NOT EXISTS` predicates through the visual builder. Conditions within a registration match share one row, and a matching-record filter does not multiply student or section counts. The new active-registration and empty-section starters advance the legacy batch-registration/headcount cases without raw SQL or grouped output. All clauses, including hidden-only fields and ancestors, require current data grants. Named relationship copies now support independent repeated branches. Nested All/Any matching cards now preserve ordinary filter scope, source permissions and result grain across saved/static/population workflows. Further derived financial aggregates remain open.

The [general engine and named joins](workflow-review.md#general-report-design-and-named-joins) now support independent copies of approved relationship branches. Applications, student records, program assignments, registrations and recorded academic credits can be connected through one permissioned registry; copied fields retain their original types, units and data grants. Acceptance tests explicitly cover distinct section headcounts below 12, including zero and withdrawn-only sections, and independent Fall/Spring requirements. The examples do not define the engine’s feature boundary. [Verified submission dates](application-submission-history.md#submission-date-reporting) now have an indexed read model populated from genuine submission events. Earlier dates stay unknown; authoritative graduation sources still require their legitimate workflow and read model.

Current [student-account reports](workflow-review.md#student-account-reports) now cover net balances and unreversed charge/payment/refund totals by student/billing term, outstanding balances, available credit and currency-separated summaries through the shared visual builder. They use an atomic balance read model rather than replaying every account in a report. Matching-record conditions select registered populations without multiplying balances. This advances the legacy account-balance example; separate tuition/fee sources and historical as-of accounts remain open; the posting extension below supplies individual detail and latest posting-event selection. Financial sources require independent finance and student-data grants.


[Latest/earliest related-row selection](workflow-review.md#latest-and-earliest-related-records) now extends the approved graph beyond the curated latest-term lookup. It preserves whole records, applies join filters before selection, leaves ordinary and existence filters in their own scopes, keeps ties by default and offers an explicit stable one-row choice. Person-linked application summaries use genuine submission-date projections and separate admissions grants. Saved/shared/static/CSV/population paths share the definition and permission checks, while amount totals still protect currency and account grain. This advances the legacy anti-join/latest-row examples without sorting term codes or returning arbitrary ungrouped values. The financial posting extension below now supplies posting detail and latest payment-posting selection. Broader historical/as-of relationships still require their legitimate read models.

[Scheduling reports](workflow-review.md#scheduling-reports) now extend the same engine to physical-room inventory, online/room booking occurrences, categories and linked retained offering/course details. Distinct counts preserve empty rooms; same-occurrence matching supports time-window questions without treating a missing booking as a room-availability approval. Timestamp filters are explicit UTC, source duties remain independent, and saved/static/export paths use the existing bounded implementation. Occupancy/duration and published-timetable-only analytics remain open.

[Conditional summaries](workflow-review.md#conditional-report-summaries) extend the existing CASE/aggregate foundation with visual per-column predicates, including side-by-side registration counts and currency-separated conditional balances. They preserve NULL versus zero, shared row/HAVING scopes, hidden-field grants, named joins and fixed captures. Conditions do not independently pre-aggregate several fact tables; broader expression trees, arbitrary CASE label mappings and financial fact-grain sources remain open.

[Financial posting reports](workflow-review.md#financial-posting-reports) now extend the account-balance/latest-payment examples with a declared posting grain, currency-separated payment summaries, original/replacement/reversed lineage and indexed account-scoped latest selection. They reconstruct from genuine protected events, preserve unknown source categories and share the existing report/save/static/export/population engine. Event times describe posting/correction chronology; they do not invent original receipt or bank settlement dates. Typed fee origins, historical as-of accounts and bank reconciliation remain open.


[Funding-method reporting](workflow-review.md#funding-method-reports) now extends financial postings with the current method enum. Conditional grant/loan totals and method-scoped latest payments reuse the existing compiler, with account/currency/posting grain, unknown-method distinctions and source permissions intact. Static captures retain earlier answers after method corrections; private receipt references are excluded. Further fee/source classifications and actual aid-award datasets remain separate acceptance work.

[Calendar period columns](workflow-review.md#calendar-period-reports) now extend dated-source acceptance across genuine application submissions, scheduled meetings and financial postings. The general column control groups approved dates by day/month/year without dropping their year or changing raw filter semantics. Monthly starters reuse ordinary joins, source permissions, typed summaries, saved/static results and existing exports; currency/grain guards still apply. Missing dates, months without records, fiscal calendars, historical as-of accounts and actual bank settlement dates are not inferred. General expression trees and broader derived fact-grain aggregates remain open.


[Custom ordered text labels](workflow-review.md#custom-labels-in-existing-reports) now complete the visual `CASE` label-mapping slice: up to eight first-match rules, explicit NULL/fallback output, shared bounded All/Any conditions, text grouping/minimum/maximum and typed counts/summary filters. Hidden predicates retain field/source/ancestor grants, root and financial totals retain fan-out/currency guards, and saved/static/shared/formula-safe export/population paths use the same validated definition. No new report source or template is added. Broader numeric/mixed expression trees, independent financial pre-aggregation and other remaining acceptance cases stay open.

[Retained reporting-group roots](section-publication.md#current-and-retained-reporting-fields) now support accepted-period rollups in the existing student-credit source. Group stable root references and use distinct students across sibling groups; retain exact original labels, row grain and the known-hierarchy flag after current reparenting. Earlier absent paths remain unknown. This adds no dataset/template, census inference, raw-event query or new financial aggregate.

[Independent account charge components](account-charge-reports.md) now advance the legacy tuition/fee/payment acceptance case: current and recorded-cutoff accounts expose side-by-side net tuition, fee, manual and unclassified amounts without joining several posting facts together. Linked credits, active replacements, reversal chronology, zero accounts, currency precision and existing fan-out guards stay explicit. Financial posting sources retain their declared detail grain; these component fields belong to the account sources. The shared save/static/share/export implementation and source permissions apply. Further institutional financial sources, arbitrary derived relationships and richer expression trees remain open.
