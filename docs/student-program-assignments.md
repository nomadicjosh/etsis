# Additional student-program assignments

Implemented 2026-11-09. Additional programs now start their history when staff create the assignment. [Closing/reopening](student-program-status-history.md) continues in the same stream, and [primary-program selection](student-primary-program-history.md) remains a separate reviewed action. [Initial matriculation](student-matriculation.md) now starts the first assignment in this same status stream; neither path invents creation events for older rows.

## Staff workflow

Open **Students → a student → Assign an additional program**. Select the academic program and its entry term, enter a reason, then choose **Review program assignment**. The review shows the program, entry term and cohort derived from the academic year linked to that term. There is no separate catalog-year field to enter.

If an applicable published curriculum revision exists, the review identifies it. If one must be created by the existing cohort setup workflow, the review says it will be created on confirmation. Merely reviewing does not create a curriculum, assignment, cohort binding or event. **Revise assignment** preserves your entered choices and reason.

If the entry term is not linked to an academic year, the review clearly says that calendar setup needs attention. Staff can confirm an assignment without a cohort and review its calendar setup separately. etsis does not guess a year from overlapping dates or silently invent curriculum requirements. Degree-audit requirements are selected through their own reviewed workflow.

**Confirm program assignment** creates an active additional assignment. The student's primary program, original institutional entry term, existing assignments, earned credits and posted charges remain connected to their existing records. Use **Make primary** separately if appropriate. This action takes effect on confirmation; it does not establish a backdated program start or record graduation or withdrawal.

An existing active assignment to the same program blocks another one. A closed assignment with the same program and entry term must be reviewed for reopening instead of recreated. Reviews expire after 20 minutes and must be repeated if they cross into another institutional date or if the relevant student, program labels, term/cohort mapping or curriculum proposal changes.

## Creation and later history

**StudentProgramWasAssigned** is the first event for a genuinely new additional assignment. It retains its identity, student/program/entry-term references, starting status, program and term labels, and the cohort/curriculum reference actually assigned, when one is available. The protected context retains the trusted actor, entered reason, operation identity and actual confirmation time.

**Program status history** distinguishes **Program assigned** from an observation of an older record. New assignments retain their creation context through later closure or reopening. The history shows the original program/term/cohort information as assigned even if today's labels or cohort assignment later change. It excludes protected reasons, actor details and raw event envelopes. Earlier untracked assignments still show **Observed current assignment**, with earlier history explicitly unknown.

If Biology is added and later closed, resending the original add confirmation does not add another Biology assignment or reopen it. etsis recognizes the completed request and returns its earlier creation result while the current assignment stays closed. The workspace reloads the current record after confirmation.

## Authorization, storage and checks

Assignment review and confirmation require `sis:registration:manage`; student ownership and `sis:student:read` alone do not grant creation authority. The command locks the student, term and program before reading the decision context and rechecks the staff actor's permission after waiting for those locks. Existing activity, primary-selection and program-status histories are verified where used. Browser mutations retain CSRF protection, private/no-store responses and suppressed debug collection. Review tokens stay in browser memory, with authenticated encryption and student/actor/purpose binding.

The assignment, derived curriculum if needed, cohort binding, creation event, checkpoint, operation receipt and required audit commit together. A failed audit or a cohort result that differs from the reviewed proposal rolls back the whole operation. The existing program-status checkpoint supports the creation event without a database schema change. All authoritative events continue to use `sis_history_events`; existing events, receipts and older observation schemas remain unchanged. No working database was migrated during this work.

Fictional integration checks cover write-free previews, existing and newly created curriculum references, explicitly unlinked terms, replay from creation, primary selection, closure and exact retries, duplicate and stale reviews, changed calendar/curriculum setup, ownership and permission rechecks, protected reasons, invalid event shapes and complete rollback. The workspace browser check covers review, revision, confirmation and history with keyboard/focus, accessibility and narrow-screen checks.

Complete admissions/lifecycle/standing decisions, backdated program corrections and operational projection rebuild/swap tooling remain later stages. An initial cohort snapshot records what was assigned at creation; later cohort corrections keep their separate existing history rather than rewriting that event.

## Specialization choices within a pursuit

Open **Students → a student → Student programs → Specializations** for the relevant program assignment. This workflow uses the exact [program publication](program-publication.md#program-specialization-setup) retained by that pursuit's matriculation cohort, including its offered choices, required count and maximum. Today's active flags, names and institutional policy do not replace those facts. Offering new choices for a later cohort does not add them to earlier students automatically.

Search by code/title and select choices with checkboxes. Pages contain at most twenty choices; searches and page changes preserve checked choices. Descriptions expand on demand. Enter a reason, choose **Review specialization selection**, inspect **Before** and **After**, then confirm. **Revise selection** preserves entered choices and reason. A rejected review leaves the form available for correction. The default published minimum is zero (optional), while each program publication determines its required and maximum counts. An empty selection deliberately records removal when that publication permits it; it does not delete history. Duplicate/foreign choices, counts outside the retained limits and unchanged selections are rejected.

Selection changes take effect when confirmed. The encrypted review binds the staff actor, student, pursuit, retained program revision, cohort-binding revision, status history, current selection position, reason and twenty-minute expiry. Confirmation rechecks current authority after the student lock and replay and checks expiry again before writing. Two competing reviews cannot overwrite each other. If staff resend an accepted confirmation, etSIS returns its original receipt without restoring old choices, even after later selections, expiry or pursuit closure.

A closed pursuit remains readable but cannot receive a new selection. A cohort change preserves its previous selection and shows a warning; staff must deliberately review a new selection against the changed cohort. Even a cohort change subsequently reversed invalidates a pending review because the binding revision changed. An earlier unversioned cohort has no inferred offered choices and requires review of its cohort/publication setup. Missing or inconsistent recorded publication evidence stops the workflow.

Reads/history require `sis:student:read`; changes additionally require the existing independent `sis:degree-audit:assign` permission. Catalog management and student ownership alone grant neither. Student self-service specialization changes are not exposed yet. Browser mutations preserve framework CSRF, private/no-store responses and debug suppression; no student data or review token enters browser storage.

**Specialization history** shows the originally selected program labels, choices, cohort revision and effective/recorded times in frozen ten-decision pages. It excludes actors, protected reasons and raw event envelopes. Each decision retains references to the exact program publication, rather than copying editable specialization definitions into student events. The per-pursuit specialization stream uses the same protected `sis_history_events` journal, expected versions, predecessor decisions and operation receipts as other academic decisions. Choice events (`StudentSpecializationsWereSelected`) and requirement assignments (`StudentSpecializationRequirementsWereAssigned`) share that stream and its ordering. Each event, current projections and required metadata audit commit or roll back together. Replay verifies the projection and uses one shared request budget across status, selection, program and explicitly inspected requirements streams (at most 400 pages/2,000 events); it performs no external effects.

`20261113000003_CreateSisStudentSpecializations` adds one ULID-keyed, reconstructible `sis_student_specializations` read model, scoped to the pursuit and student, with references to the retained program/year. It adds no event table or permission grants and creates no selections from existing rows. The configured application database was inspected before migration; the additive migration was applied with before/after comparisons verifying that existing academic history, student/cohort records, specialization setup and access grants were unchanged. The schema compiles for the framework's five supported dialects; SQLite tests and the local MariaDB migration are execution checks, not certification of every driver.

Specialization choices record academic intent. Staff can [compose, publish and independently test specialization requirements](degree-audit-builder.md#specialization-requirements), then assign an exact publication using the workflow below. These decisions do not allocate courses, change earned credits/GPA, confer an award or post charges. Combined degree/specialization sharing, exclusions and degree-progress evaluation remain subsequent work. Fictional checks cover retained labels/limits, required/empty choices, cohort changes, stale/expired/wrong-actor reviews, permission rechecks, closed pursuits, original retries, unknown earlier cohorts, projection corruption, protected history, frozen pages, replay bounds and audit rollback. Provider/router checks include CSRF and private responses; browser checks include keyboard use, preserved checkbox drafts, paging/search, narrow-screen accessibility and literal text rendering.

### Assign published specialization requirements

From a recorded choice, choose **Requirements for … → Choose a requirements publication**. The chooser pages through published versions, showing which match this pursuit's exact retained program revision. A matching specialization name or academic year alone is insufficient: the specialization, program, academic year and program publication must all agree. Other revisions remain visible with an explanation and cannot be assigned. If none are published, a catalog author must first publish the matching requirements.

Enter a reason, choose **Review publication …**, inspect the previous and proposed versions, then **Confirm requirements assignment** within twenty minutes. **Inspect reviewed requirements** opens the existing full-width requirements preview; returning preserves the same review. **Revise requirements assignment** preserves the entered reason. A rejected review keeps the reason available for correction. **Inspect assigned requirements** resolves the exact retained publication, groups and program definition. Later publications never replace the assigned version.

Unchanged choices keep their assigned publications when other choices are added or removed within the same cohort binding. Removing a choice removes its current requirements binding, while preserving the original event. Adding that choice again requires a fresh requirements assignment; it does not silently restore the earlier one. A cohort change leaves earlier requirements inspectable with a warning. Staff must review the specialization choices against the new cohort before assigning new requirements; that choice review clears the old bindings. Changing the cohort and changing it back still requires fresh reviews.

Reads and inspection require `sis:student:read`. The chooser, review and confirmation additionally require `sis:degree-audit:assign`; catalog-management permission is unnecessary for these student decisions. Closed pursuits remain readable. Actor/authority, pursuit ownership, cohort revision and stream position are checked again after waiting/replay. A repeated accepted confirmation returns its original receipt after later assignments, removal, expiry or closure, without restoring the earlier binding. Competing or expired unconfirmed reviews write nothing. Required audit failure rolls back the event, receipt and both projections.

After assignment, **Review specialization progress** opens an [independent comparison](student-degree-progress.md#assigned-specialization-review) against verified current work. It uses the exact retained publication, with captured minimum, placement and contribution details and an explicit refresh. Student-specific exceptions and cross-component sharing/exclusions are not applied in this comparison; it does not establish combined degree completion.

**Specialization history** includes choices and requirements assignments in the same frozen ten-decision pages. It shows retained names, publication numbers and effective/recorded times, excluding protected reasons, actors and raw events. Full requirement definitions are resolved only on explicit inspection or assignment review, rather than once for every choice on the base screen.

`20261113000005_CreateSisStudentSpecializationRequirements` adds the ULID-keyed `sis_student_specialization_requirements` projection, unique per pursuit/specialization. Its small retained reference is checked against replay of the existing specialization stream. It contains no copied requirement tree, additional event journal or inferred earlier decisions. The migration adds no access grants and preserves the existing choice projection. The migration was applied to the configured MariaDB database after bounded inspection; before/after comparisons verified unchanged student/cohort records, catalog setup, access grants and all twenty existing journal events with their stream heads and receipts. The new projection remained empty: no student assignments or historical facts were invented. Five-dialect compilation, SQLite execution, actual provider/router/CSRF checks and fictional browser workflows cover this addition. Combined allocation and specialization-scoped exceptions remain the next stage.
