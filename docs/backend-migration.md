# Backend migration to CodefyPHP

For the current order of work, relative effort and release criteria, see the [development roadmap](development-roadmap.md). The coverage below describes implemented foundations and their limits.

The target remains PHP 8.4 or newer, with the Application, Domain, and Infrastructure namespaces in composer.json. Legacy source is reference material and is not included at runtime. The new backend follows the existing `src/Domain/User` layout: each domain context owns its business services, repository contracts, commands, queries, DTOs, enums and value objects. Application owns HTTP/console entry points and provider wiring; Infrastructure implements persistence, security, clocks, identity generation and external integrations. See [domain organization](domain-organization.md). Staff workflow redesign recommendations and their implementation status are maintained in [workflow-review.md](workflow-review.md). The administration workspace and portal now connect these foundations; see [backend workspace](backend-workspace.md) and [campus portal](campus-portal.md).

## Highest-priority historical-integrity work

[Published section details](section-publication.md) now retain explicitly reviewed instructional dates, capacity, delivery, canonical faculty identity, term context and fees. Their protected history, private staff workflow and retained registration/academic references are implemented. Reviewed amendments select the version for later registrations without rewriting existing student references or charges; offering-plan activation now retains reviewed section versions and instructional dates atomically. Complete section/policy coverage remains staged work. Publication alone does not change existing academic or financial records.

[Event sourcing](event-sourcing.md) now governs security and historical academic integrity ahead of feature expansion, superseding the earlier finance-only assumption. The [architecture review](event-sourcing-architecture.md) distinguishes current protections from the required retrofit: secure event storage/envelopes, immutable published academic definitions, then canonical credit/grade and registration histories. The [legacy field review](academic-history-field-review.md) identifies missing course, section, program and academic-record fields and their normalized ownership.

The functional coverage below does **not** mean these contexts already provide complete event sourcing or historical reconstruction. Institutional creation/grade/drop now uses [replayable academic-credit history](academic-credit-history.md), and [transfer award decisions](transfer-credit-history.md) now use the shared journal, while some student/program changes still update mutable rows; metadata audit and encrypted receipts alone cannot reconstruct every prior state. Restore missing historical context together with versioned definitions and the appropriate event streams, rather than layering more mutable fields onto those gaps.

[Registration history](registration-history.md) now retains accepted enrollments and early/late releases, with committed section order, replay-derived enrollment rows and registrar-only history. Request-arrival/waitlist history and complete section/lifecycle versions remain staged work.

## Source review and scope decisions

`legacy-inventory.json` records documentation, migration tables/columns, view fields, router declarations, module functions, and source checksums. The review now includes 51 documentation files, six legacy migrations, 207 PHP views, 29 routers, and ten module files. The newly supplied module routers and views resolve the earlier missing-source question; missing behavior may also be reconstructed under the user's instruction.

The legacy architecture mixes Liten route closures, database writes, global functions, HTML generation, and hooks. Registration writes both section enrollment and academic-credit snapshots; admissions creates the student and program records; registration hooks generate bills. The 2017 migrations rename academic records to STAC, STCS, SACP, STAL, and STTR. The new design preserves those workflow distinctions without retaining raw SQL terminals, paid-module checks, integer entity identities, or callable rule text.

Database support targets the framework's five implemented drivers: MySQL, PostgreSQL, SQLite, SQL Server, and Oracle. The user authorized this fallback when universal PDO support is impractical. PDO provides a common connection/statement API, but not universal DDL, catalog discovery, LOB handling, or transaction/savepoint syntax. Firebird, DB2, ODBC and other drivers would need additional dialect implementations and integration environments. The framework factory and schema compilers currently cover five; vendor code has not been modified.

`config/database.php` now exposes all five connection names (`mysql`, `pgsql`, `sqlite`, `sqlsrv`, `oci`) using the existing DB_DSN/DB_USER/DB_PASSWORD configuration. New migrations use the framework schema abstraction, ULID primary keys, portable integer/string/date/text types, explicit foreign keys, and no database enums or auto-increments.

## Transaction and privacy behavior

Registration locks the student first, then the person for hold eligibility, then the section, protecting both per-student limits and section capacity. Enrollment, academic credit, applicable term charges, section charge and audit write commit together. A billing/currency failure rolls them all back. Repeating an existing active registration returns it without charging again. Early drops delete enrollment/academic-credit rows and reverse the original course charge in the same transaction, preserving encrypted drop receipts and financial event history. Later drops retain the course and charge with the dated term-policy grade and zero earned credit. The entire institutional drop/add deadline date is included; GPA follows the selected catalog grade. Charge reversals may leave account credit and do not issue cash refunds.

Row locking uses current locking reads for MySQL/PostgreSQL/Oracle, update-lock hints for SQL Server, and a write followed by an existence check for SQLite. Transactions acquire their serialization locks before reading mutable state. Bookings serialize approvals per room before checking every occurrence using bounded existence queries. Timesheets serialize entries and decisions per employee. Final-grade and score writes verify the section's assigned faculty identity or an explicit administrative permission; a request cannot supply a teacher identity to bypass access.

`PortableTransactions` joins nested operations into one PDO transaction. This avoids the database layer's generic SAVEPOINT/RELEASE syntax, which does not work consistently for SQL Server and Oracle. Nested failures mark the transaction rollback-only, even if caught by application code. Application-owned outer boundaries commit or roll back; when joining a transaction owned by external code, that external owner remains responsible for rollback when an exception propagates. Existing user event/projection persistence uses this same boundary.

The [course publication workflow](course-publication.md) now preserves explicitly reviewed code, catalog/transcript titles, description, fixed credits and prerequisite identities as immutable definitions in the existing protected event table. It includes staff review/publish/history controls, actor-bound retry handling and audit rollback. Empty sections can now explicitly retain a reviewed publication; portal/registration/staff reads and new institutional credit references use it. Offering-plan publication now requires explicit definition selection, with atomic binding/activation and actor-bound receipts. Earlier unbound/directly created and transfer records keep their staged behavior. Remaining legacy fields, complete section/policy revisions and their retained attempt references remain pending; institutional credit creation, grades and drops now use the shared journal. `20261108000003_CreateSisCourseDescriptionsTable` adds draft and rebuildable published-text storage; `20261108000004_CreateSisCourseVersionBindings` adds normalized retained-definition and section/credit reference projections without backfilling old records; new registration/transfer credits snapshot the published transcript title, while existing records remain unchanged.

SIS foundation routes are under `/sis/`, return JSON except explicit roster/report-page CSV downloads, and retain the framework's global CSRF protection. Forms use parsed bodies; the course importer specifically accepts text/csv. Timestamps require ISO values with explicit offsets. Owner checks use the signed-in Gate identity, not request-supplied owner/employee/faculty identities. Staff permissions are explicit; the existing admin role receives the SIS group. Transfer evaluation normally combines `sis:transfer:manage` and `sis:student:read`; catalog editing and official transcript-request processing remain separate grants. See [registrar duties](authorization.md#registrar-duties-and-academic-access).

SIS responses, including errors, are private/no-store. Debug middleware excludes SIS requests before collectors are resolved. Error normalization suppresses exception payloads. Audit and delivery records contain references/metadata, never message bodies. Campaign content is encrypted with the application's existing configured key. The live transport refuses mail debug-file mode and sanitizes upstream failures.

For opt-in live mail, configure `SIS_MAIL_ENABLED=true`, `SIS_MAIL_FROM`, and the existing mailer DSN securely. No credentials are placed in a migration, job, test fixture, or source file. No message has been sent during development or verification. Transport tests use fictional recipients and injected providers.

## Institutional student/staff IDs

A person's ULID remains the internal primary key. Their separate `institutional_id` is the human-facing ID shared by student and staff roles. One person who is both a student and an employee has one current institutional ID. It is a string, so values such as `00001234` retain leading zeros. Values are trimmed and uppercased; 1–32 ASCII letters, digits, dots, dashes and underscores are accepted, starting with a letter or digit.

Creating a person without a value, or with a blank value, generates a `P-` prefix followed by 12 random uppercase hexadecimal characters. The generator is an application port that can later be replaced with an institution-specific numbering policy. Generation retries database uniqueness conflicts within a bounded number of fresh transactions. Manually assigned IDs are unique across people and conflicting assignments are rejected.

The new `CreateSisPersonIdentifiersTable` migration stores the canonical ID and optimistic version in a person-owned one-to-one identity record. It backfills existing people who have no identity record, and preserves existing IDs and versions when rerun. Existing person/student/employee/enrollment/financial keys are not changed. Student and employee profiles, statements, transcripts, gradebook scores and student reports resolve the current institutional ID through the person relationship. Consequently, an edit appears on subsequent reads without copying the new ID into every child record or rewriting financial events.

`sis:person:manage` allows person creation and staff lookup. Manually assigning an ID on creation, changing it, or clearing it to request a new generated ID also requires `sis:person:assign-id`. This permission belongs to the existing SIS admin group by default and can be granted to appropriate registrar/HR roles. Record ownership alone does not permit changing an assigned ID. The RBAC configuration now has one SIS permission group and role permission lists contain names only; duplicated nested groups from the earlier foundation were removed and the initial seed loader is tested. Runtime grants now come from the database; see [authorization](authorization.md).

HTTP foundation:

- POST `/sis/persons/`: optional string `institutional_id`; the response includes the assigned ID and `identity_version`.
- GET `/sis/persons/{id}/`: owner or authorized staff read, including current ID/version.
- POST `/sis/persons/{id}/institutional-id/`: `institutional_id` plus the last read `identity_version`. Blank/missing IDs generate a replacement; stale versions and duplicate IDs are rejected.
- POST `/sis/persons/lookup/`: staff lookup by `institutional_id`. The ID is carried in a protected body rather than a URL segment.
- GET `/sis/employees/{id}/`: owner/HR employee profile with the current institutional ID.

All these routes keep the existing CSRF, authorization, no-store and debug suppression rules. ID changes and their audit metadata commit atomically; audit entries contain actor/person references, not the old or new institutional ID values. The person workspace now includes creation and institutional ID forms. The new migration has not been run against an institutional database.
