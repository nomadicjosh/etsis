# Reviewed Moodle person links

The person workspace offers **Moodle account link** for an existing account and **Create a Moodle account** for reviewed request intake. Existing-account linking is operational. Reviewed creation now has a bounded background worker and a retry-safe Moodle connector endpoint. Both intake and processing default off. With approved setup and processing enabled, the worker creates the account and retains its Moodle ID automatically; no second linking task is required. Automatic student/faculty eligibility and section access remain later stages.

The intended integration automatically provisions eligible **students** and **faculty** in the background when the institution enables that capability. An accepted teaching assignment must request provisioning of the instructor and the appropriate role in that specific Moodle course; committed registrations drive student course access. For all other people, staff choose creation or existing-account linking on an as-needed basis. Such people do not need a student or faculty role just to receive a Moodle account. See the [provisioning policy](optional-moodle-integration.md#automatic-account-provisioning-and-section-access) for the intended workflow and current implementation status. Normal SIS work remains available without Moodle.

## Setup and permissions

Complete the [optional Moodle setup and installation approval](optional-moodle-integration.md) first. Person linking requires the independent protected permission **sis:moodle:link-person** and **sis:person:manage**. Moodle administration alone does not grant it. The migration adds no role/user grants and no broad permission implications; grant it through an institution-created role or a direct assignment to appropriate administrators.

For a manual link involving a person with a local sign-in account, existing account-management authorization also applies: **admin:profile** for one's own account or **admin:edit:user** for another account. Only a super administrator may manually link a super account. This tool does not create or enable a local sign-in account. Planned automatic provisioning will use its own institution-approved service authority and current eligibility checks; it must not require a staff member to approve every normal student/faculty account individually.

The restricted Moodle service must authorize these functions:

- `core_webservice_get_site_info`
- `local_etsis_get_instance_info`
- `core_user_get_users_by_field`

The connector's predefined **etSIS instance verification** service contains only the first two functions. To authorize person lookup, create a separately reviewed restricted custom service with the three functions, explicitly authorize the integration account, and configure its token securely in etSIS. For account creation, the separate provisioning service described below also includes this lookup. Moodle's predefined plugin service cannot be expanded through the administrator UI. See Moodle's [service creation documentation](https://moodledev.io/docs/5.3/apis/subsystems/external/advanced/custom-services). Do not grant course creation, enrollment or gradebook functions for this workflow, and do not broaden unrelated role capabilities merely to make discovery flags available.

## Link an existing account (implemented)

1. Search **People** by name or institutional ID, open the person and select **Moodle account link**. No Moodle request runs while searching people or loading saved link details.
2. Enter the exact numeric Moodle user ID independently verified for this person, plus an administrative reason. Do not enter credentials, student academic details, an email address or username. etSIS does not infer identity from matching names or email addresses.
3. Select **Review Moodle account link**. The server verifies the approved installation, requests exactly one ID and verifies the installation again. The screen displays only the entered reference and known/unknown suspended/deleted flags. It does not display Moodle names, email addresses or profiles.
4. Check the independent-verification acknowledgement, then select **Approve reviewed person link** within 20 minutes. etSIS repeats the bound lookup and checks that the person, installation and reviewed flags have not changed. Approval and its audit commit atomically.

**Cancel link review** saves nothing. **Back to person** returns to the connected person workspace. **Refresh saved link** rereads local state without contacting Moodle, including after a response was interrupted. Retrying the same completed review returns its original link without a repeated external check or approval audit, even after expiry or disabling the integration; current authorization and the original approved binding still apply.

Missing records and records outside the service account's scope are both described as **no matching account returned**. A known suspended/deleted account cannot receive a new link. A missing flag remains **not supplied by Moodle**, rather than becoming false. Staff may independently approve a reference with unknown flags, but that does not establish current login eligibility. Future SSO must apply its own current account checks and institutional policy.

Saved references have no ordinary replace/unlink action. A correction needs a separate reviewed workflow that preserves the previous decision and checks any dependent mappings. Changing an institutional person ID continues to resolve through the same person ULID; it does not move the Moodle reference to a different person.

## Review a creation request (implemented)

Creation intake requires the independent protected permission **sis:moodle:create-person** together with **sis:person:manage**. Existing-account link permission and Moodle administration do not imply creation authority. The same local-account and super-account protections described above apply. The migration adds no role/user grants. This workflow supports people without student or faculty roles.

Upgrade the Moodle connector to **0.3.2-alpha**, configure its restricted provisioning service and supported authentication modes, then enable `SIS_MOODLE_ACCOUNT_REQUESTS_ENABLED=true` alongside the enabled integration and approved installation. Set `SIS_MOODLE_PROVISIONING_ENABLED=true` separately to permit external creation. The status `processing_available` reports this configured permission to process, not an end-to-end health check or proof that the scheduler is running. See the [connector setup guide](../integrations/moodle/local/etsis/README.md).

1. Search **People**, open the person and choose **Create a Moodle account**. Status reads stay local. An existing link or saved creation request prevents another request.
2. Review the person's canonical name. Username and email are prefilled from their local sign-in account when available; enter or correct only those account attributes. No password is requested or copied.
3. Select **Institutional SSO** or **Moodle password-setup email**, and give a short administrative reason. Review verifies that the selected mode is currently enabled in the approved connector and retains its authentication-policy fingerprint. The institution must separately verify its identity-provider and mail setup.
4. Select **Review account request**. etSIS verifies the approved installation and displays the exact name, username, email and sign-in choice. Acknowledgement is required before **Save reviewed creation request**. Reviews expire after 20 minutes and cannot be used by a different administrator or for another person.
5. Confirmation verifies the installation and authentication policy again, checks current permissions, profile, account defaults and binding, then saves the encrypted approval, reference-only outbox entry and audit atomically. The browser mutation queues work; it performs no account creation itself. The workspace reports **queued**, with a clear notice when processing is disabled.

**Cancel review** saves nothing. **Refresh request status** rereads local state after an interrupted response. Repeating the same successful confirmation returns the saved request without another approval audit or remote check, even after review expiry or intake disablement; current authorization and the original binding still apply. A saved request blocks a competing manual link, including a link reviewed before the request was saved. There is no saved-request cancellation or replacement workflow yet.

## Process a reviewed account request (implemented, opt-in)

After installing and configuring the new connector/service, run:

```sh
ddev codex sis:moodle:provision
```

Without DDEV, use `codex sis:moodle:provision` with the application's configured PHP runtime. Schedule this bounded command once per minute through an institution-managed scheduler when ready. It processes at most one request per invocation and makes no network/queue request when disabled. No scheduler is enabled automatically by this change.

The worker claims a reference with a version and a five-minute lease. It decrypts the approval only in memory, checks its digest/references and verifies the current requesting user's database permissions, person/profile/defaults and approved installation. Short local transactions lock the existing account/person boundaries; remote requests run after those transactions finish. Before retaining the result, the worker checks local authority again. The link, completion state and attributed audit commit together. If that transaction fails, the original remote operation remains available for reconciliation.

The connector checks the installation fingerprint and exact reviewed authentication-policy hash before effects. Its receipt and newly created Moodle account commit in one Moodle transaction. Repeated identical operations return the original account ID; existing usernames/emails are refused rather than silently adopted. An uncertain response leaves the original operation pending until its lease expires. At most five external attempts are permitted; a subsequent run marks it for review. Completed and review-required items are not automatically reclaimed.

For **Institutional SSO**, the connector creates the Moodle-side record under the configured external authentication plugin, without modifying an identity-provider password or granting roles. This does not establish an SSO trust relationship or create an identity-provider account. Verify the chosen plugin's account-matching requirements independently.

For **Moodle password-setup email**, the connector creates a manual-authentication account with an unknown random internal password hash and requests a native one-use password-reset link. It never emails a generated password. A committed attempt marker prevents blind resend after interruption. If delivery fails or becomes uncertain, the worker retains the account link and reports that password recovery needs review. Use Moodle's normal password recovery for that existing account; do not create another account. Moodle accepting email is not proof of recipient delivery.

Requests from the earlier intake stage lack an authentication-policy fingerprint and stop for review; no policy is fabricated for them. Changes to permissions, profile or approved policy also require reconciliation. [Original receipt inspection](moodle-account-reconciliation.md) now checks uncertain outcomes without retrying creation, sending email or changing a link. The setup-email resolution below closes a warning for an account that is already linked. Reviewed recovered-link attachment, request corrections and replacements remain subsequent stages: preserve the original operation and ask an integration administrator to review it before any new request or database repair. Automatic faculty/student provisioning and course-role synchronization remain subsequent work; staff-requested creation does not require those roles.

## Resolve a setup-email review (implemented)

When the worker has retained a Moodle account link but reports **setup email needs review**, first resolve the person's access through the institution's verified support process or Moodle's normal password recovery. Keep the existing account. This step must not involve copying a password or reset link into etSIS.

1. Open the person's **Create a Moodle account** workspace. The saved request shows the retained Moodle ID and **Resolve setup-email review**. The option appears only for a linked account with the specific setup-email issue; it cannot close an uncertain creation, exhausted retry or changed-request warning.
2. Enter a short administrative description of how access was resolved, without credentials, reset links or academic details. Select **Review access resolution**.
3. Check the displayed person, existing Moodle account and outcome. Acknowledge that you verified access was resolved, then select **Save access resolution** within 20 minutes. **Cancel resolution review** saves nothing.
4. The request becomes **completed**, with a note that staff recorded the resolution. This records the staff statement; it does not independently prove email delivery or a successful Moodle sign-in. No message is resent, account recreated, password changed or link replaced.

The same creation/person/account permissions and super-account protections apply. A different currently authorized staff member may review the warning; confirmation belongs to the administrator who prepared that review. Review and confirmation are entirely local and remain available when intake, provisioning or Moodle connectivity is disabled. Permission loss, a changed person/profile, installation, link or request version invalidates an outstanding review. An interrupted response can be recovered with **Refresh request status**. Repeating the same successful confirmation returns its original result without a second audit or evidence update, including after expiry; current authorization and the retained request/link still apply. A competing review cannot replace the saved resolution.

Migration `20261112000004_CreateSisMoodleAccountResolutions.php` adds nullable resolution-digest and encrypted-evidence columns to the private account-request table, leaving earlier approvals and operation IDs intact. The evidence retains the reviewing actor, request/link/binding references, reviewed reason and actual UTC confirmation time. It is saved with a version-checked outbox transition and attributed audit in one transaction. The outbox remains reference-only; ordinary status omits the reason and encrypted evidence. This does not create another event store or alter academic facts. POST `/sis/people/{person}/moodle/account-request/resolution/review/` and `/resolution/confirm/` retain framework CSRF, private/no-store responses and suppressed debugging.

## Security and persistence

`20261111000007_CreateSisMoodlePersonLinks.php` adds `sis_moodle_person_links` and the independent protected permission. Its primary key is a ULID; Moodle's numeric identifier is an external string reference. Foreign keys retain the person and installation approval. Unique constraints on `(binding_id, person_id)` and `(binding_id, moodle_user_id)` protect both sides against competing approvals. The reason, reviewed status and local-person revision are encrypted; ordinary status responses omit that review evidence. The table is excluded from ordinary reporting sources.

`20261112000000_CreateSisMoodleAccountRequests.php` adds ULID-keyed `sis_moodle_account_requests` and `sis_moodle_provisioning_outbox`, plus the independent creation permission. Request approvals contain encrypted reviewed attributes and reason, with actor/time, binding/person references and a review hash. Unique `(binding_id, person_id)` prevents duplicate requests. The outbox contains only its ID, request reference, state/version, lease/attempt metadata, fixed issue code and creation time; it contains no profile, credential or upstream response. The SQL outbox shares the approval/audit transaction; filesystem queue dispatch alone would not provide that atomicity. `20261112000001_CreateSisMoodleProvisioningLeases.php` adds the lease, attempt count and fixed issue code without changing existing approvals. These private tables are excluded from ordinary reporting sources. Application encryption keys must be retained securely for approved evidence to remain readable.

Creation routes are GET `/sis/people/{person}/moodle/account-request/` and POST `/review/`, `/confirm/` beneath it. They preserve private/no-store responses, framework CSRF protection and suppressed debug collectors. Attribute previews are transient browser memory only. Review/confirmation checks happen before the short person/account-lock transaction, never while holding those locks. Request saving does not change an academic record or add events to the authoritative event store.

These are audited integration references, using the existing permission and account boundaries. No academic record, person profile, local account, role grant or authoritative event is rewritten, and no parallel event store is introduced. Tokens, Moodle profiles, raw responses and installation identifiers are never saved in the link table or returned to the browser. The user-entered Moodle ID is visible only in this authorized person workflow and must remain out of logs and public URLs.

GET `/sis/people/{person}/moodle/` loads local saved state. POST `/review/` and `/confirm/` under that path retain framework CSRF protection, private/no-store responses and suppressed debug collectors. Reviews are encrypted, purpose-specific and bound to the administrator, person, installation, profile revision, external ID and known/unknown flags. Reviews stay in browser memory and are discarded when their view is removed. Authorization is rechecked around remote reads and within the write transaction; failures roll back both link and approval audit.

The bound reader uses one captured configuration, TLS verification, no redirects/cookies/retries and the existing response-size/depth limits. Up to four requests run outside database locks: site handshake, installation identity, one exact-ID lookup and installation identity again. They share a 30-second request budget; a final stream read can extend the operation by up to its bounded five-second read timeout. Confirmation performs a fresh operation with the same limits. Ordinary saved-link reads use the indexed local reference and do not replay history or lock streams.

A different site/installation stops the operation. A full Moodle database clone can retain the same identity, so these checks do not detect every clone or independently prove ownership. Keep clones disconnected and follow institutional recovery review. Future SSO and synchronization must use these approved references and verify the active installation before external effects; they remain subsequent stages.

## Validation

Tests use fictional Moodle responses and isolated SQLite fixtures. They cover installation changes around a lookup, configuration changes, unknown flags, stale/expired reviews, actor/permission changes, protected super accounts, uniqueness on both sides, atomic audit rollback, owned-account authorization and repeat confirmation. The schema compiles for MySQL, PostgreSQL, SQLite, SQL Server and Oracle. Browser checks cover explicit keyboard approval, narrow-screen accessibility, cancellation, private transient state and recovery after an interrupted response. No live Moodle person record was used as a test fixture or linked automatically.

Creation and worker checks cover both sign-in modes, encrypted approval storage, reference-only outbox fields, stale claims, interrupted responses, current authorization/profile checks, audit rollback and retry reconciliation. The connector contract sandbox uses fictional database, authentication and mail adapters to exercise receipt atomicity, refusal of changed retries and prevention of duplicate emails. Native Moodle tests are supplied separately; the local Moodle installation has no dedicated PHPUnit database configured, so these were not run against its application database. Institution-specific Moodle/SSO/mail acceptance remains required. No live account or email was created during development.

Setup-email resolution checks cover unchanged original approvals/links/history, encrypted evidence, current person/account/super authority, stale or competing reviews, expiry, audit rollback and idempotent confirmation. Real application routes verify CSRF refusal, private JSON and debug suppression. Browser checks cover explicit keyboard acknowledgement, cancellation, interrupted-response recovery and narrow-screen accessibility. The additive migration compiles for all five framework database dialects and has been applied to the configured MariaDB test installation.
