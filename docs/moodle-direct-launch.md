# Direct Moodle launch

The optional **Moodle** link in the signed-in portal opens `/portal/moodle/`. **Open Moodle** uses the current person's approved account link. It does not ask students or faculty to enter a Moodle ID, match accounts by email, create an account, assign a role, or synchronize academic records. Institutions enable launch separately from account provisioning.

The applications retain separate native cookies and encryption keys. The originating etSIS authentication deadline governs linked Moodle access. Moodle activity does not extend that deadline. Signing out of etSIS, successfully signing in again, switching accounts, changing credentials or deleting the local account ends the old linked access when Moodle next checks it. Other devices remain independent.

Moodle can end a session earlier under its own idle timeout, authentication, MFA or account policy. Opening Moodle again from an active etSIS sign-in starts a new linked session. Signing out **in Moodle** ends that Moodle session only; it does not currently sign the user out of etSIS. Already displayed/downloaded information cannot be recalled.

## Setup

1. Apply etSIS migrations, including `20261112000003_CreateSisMoodleLaunches.php`. This adds private launch references and an owner/person lookup index without rewriting academic history. Keep the existing approved Moodle installation and verified person links.
2. Upgrade the existing Moodle connector with [local_etsis 0.6.0-alpha](../dist/moodle/local_etsis-0.6.0-alpha.zip). Use Moodle's normal plugin upgrade; do not uninstall it. Upgrading preserves its installation identity and provisioning receipts. Moodle 4.5 or later is required. Do not enable launch until deployment acceptance below passes.
3. Generate a dedicated random 256-bit secret, represented by **64 lowercase hexadecimal characters** `openssl rand -hex 32`. Supply the same secret securely to etSIS as `SIS_MOODLE_LAUNCH_SECRET` and Moodle as `$CFG->local_etsis_launch_secret` in protected deployment configuration. Do not reuse the REST token, application encryption key, passwords or native session keys. Do not place the secret in command arguments, browser settings, the repository or logs.
4. In Moodle's **Local plugins → etSIS connector**, enable the connector, set **Trusted etSIS HTTPS base URL** to the exact canonical institution URL, and enable **direct etSIS launch**. It must be the same browser origin users visit. No wildcard or alternate-origin matching is permitted.
5. In etSIS deployment configuration, set `SIS_MOODLE_ENABLED=true`, the approved canonical `SIS_MOODLE_URL`, and `SIS_MOODLE_LAUNCH_ENABLED=true`. Keep authentication cookies secure and use HTTPS at both applications. Launch itself does not need a Moodle REST token; approval/linking/provisioning retain their separately configured services and permissions.
6. Both servers need trusted TLS connectivity and synchronized clocks. If Moodle needs a private CA to reach etSIS, supply its trusted bundle through `$CFG->local_etsis_launch_ca_file`. TLS verification cannot be disabled. This is independent of `SIS_MOODLE_CA_FILE`, which covers etSIS-to-Moodle REST calls.
7. Sign in with a fictional linked account and complete acceptance checks before permitting real students or staff to use this alpha feature.

Actual institution settings, secrets, cookies and Moodle plugin files are not changed by installing etSIS source code or running its tests. Disabling either launch flag stops new launches and makes existing linked sessions fail their next check. Unmarked native Moodle sessions remain governed by Moodle. Removing the connector or its hook removes enforcement; treat connector deployment as part of the institution's authentication security boundary.

## Request flow

1. A signed-in user submits a framework-CSRF-protected POST to `/portal/moodle/launch/`. The server derives the canonical person and current approved Moodle link from the authenticated owner. Browser identity/destination fields have no authority.
2. etSIS generates a random one-use credential and persists its SHA-256 digest. Its lifetime is at most 60 seconds and never exceeds the parent sign-in deadline. A private HTML page submits it by POST to the fixed approved Moodle installation's `/local/etsis/launch.php`. There is an ordinary keyboard-accessible button if automatic submission is unavailable. No credential appears in a URL or browser storage. The response permits only the approved form destination and uses `strict-origin` referrer policy: `no-referrer` would suppress the Origin needed for login-CSRF protection.
3. Moodle requires POST, no query string and the exact trusted browser Origin. Missing, `null` and foreign origins are rejected. It exchanges the credential through the authenticated server channel. The etSIS database conditionally consumes the credential once; retries cannot mint another grant. A lost exchange response requires a new **Open Moodle** action.
4. Moodle verifies the exact returned account is confirmed, active, not a guest/site administrator and has an enabled authentication plugin. It uses native `complete_user_login`, retaining native session rotation and login hooks. No MFA-bypass flag is set. A Moodle site-administrator account receives an explicit explanation and a normal Moodle sign-in option. This restriction does not block signing into etSIS. Other connector launch failures show fixed local guidance rather than links to nonexistent Moodle Docs pages. A different already-signed-in Moodle account must be signed out first, avoiding account-state mixing. The destination is fixed at Moodle's `/my/`.
5. A Moodle `core\hook\after_config` listener checks marked sessions before request handling, including cookie-authenticated AJAX and PHP file-delivery requests. It verifies the original deadline locally and then makes a fresh server check. Invalid or unavailable authority terminates the Moodle session and stops the request. Ordinary unmarked sessions and CLI processing do not use the channel. The launch receiver is exempt from this previous-session check because it performs its own strict origin and credential validation.

Checks have a one-second connection timeout and a three-second total network timeout, a 4 KiB response limit, TLS verification and no redirects, cookies, retries or cached positive results. One synchronous validation round trip per marked PHP request is a deliberate first-stage cost. It can affect latency and availability; test this on the intended servers. No global scan, stream replay or academic write lock is used. A validated request already in progress can finish if logout occurs after its check. Any future positive cache or background validation must explicitly define its extra revocation delay rather than silently weakening this behavior.

## Machine channel and storage

Only the exact `/sis/moodle/session-channel/` path enters a dedicated machine-authenticated middleware before browser CSRF handling. Other browser mutations retain framework CSRF protection. Requests use timestamp/nonce/HMAC authentication with separate request and response purposes, a 30-second clock tolerance and response binding to the caller's fresh nonce. The secret is never sent. Single-use exchange and non-extending checks prevent replay from granting renewed access. Private responses suppress debugging and omit raw errors.

`sis_moodle_launches` stores ULID references to the source sign-in, owner, person, approved installation/link, external Moodle ID, credential digest, ticket/session deadlines and consumed state. It contains no cookie, password, REST token, raw ticket or academic payload. These are expiring authentication support records, excluded from reporting, rather than invented domain events. References are deliberately retained independently of deletions so missing owners, links or authority always deny access. Retain login revocation tombstones until their original expiry. The [session-retention command](sign-in-session-retention.md) now previews and explicitly removes bounded batches after original expiry plus a grace period. It preserves unexpired revocation records and parent sign-ins with retained launch references. Do not delete active references to fix an access problem.

Moodle stores only the grant reference, Moodle user ID and original deadline in its native session. Core Moodle owns session retention; the connector's privacy metadata declares the minimal server exchange. Grant checks revalidate current installation approval, configured destination, canonical ownership, exact account link and source credentials. No raw event streams are exposed.

## Acceptance and current limits

Automated etSIS checks use fictional accounts, SQLite fixtures, actual framework routing/Gate/CSRF, signed exchange responses and an isolated connector sandbox. They cover expired/reused credentials, owner/link/installation changes, logout, password changes, forged/missing Origin, altered/oversized responses, unavailable authority, disabled authentication, suspended accounts, site administrators and original-deadline enforcement. The schema compiles for the five database dialects supported by the framework; other PDO engines need framework adapters. A browser check confirms the cross-origin POST sends the required Origin with `strict-origin`.

Native Moodle tests are supplied in `tests/linked_session_test.php` inside the ZIP. Run them only with a dedicated Moodle PHPUnit database. The development Moodle installation currently has no isolated test database configured; native installation/login/MFA/session-backend acceptance has **not** been established by the contract sandbox. No real account was launched or mail sent by these checks.

For each supported Moodle deployment, verify plugin upgrade preserves identity/receipts; trusted-origin POST with keyboard fallback; active/disabled/suspended and mismatched accounts; local MFA policy; expiry; source logout/reauthentication; AJAX and private-file refusal after revocation; failed TLS/timeout refusal; independent devices; Moodle-only logout; and unchanged normal Moodle login. Exercise the actual reverse proxy, session backend and expected concurrent load. Institutional OIDC, coordinated activity renewal, bidirectional logout, gradebook import and native institutional acceptance remain separate stages.
