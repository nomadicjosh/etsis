# Campus workspace

Admissions follow-up uses aligned assignment/due-date filters, explicit refresh and paging above the cards; returning from a case retains the accepted queue context. Policies gives each institutional rule its own field group/save status and preserves independent drafts. Start an application separates applicant/intake setup from the published form, with an explicit setup return that resumes the same in-memory draft and fresh answers for different context. See [Admissions workbench](admissions-workbench.md). These presentation changes preserve existing reviewed commands and private access.


The Bootstrap 5 workspace is served at `/admin/`. Views live in `resources/views/backend/workspace`; styles and behavior live in `public/assets/css/workspace.css` and `public/assets/js/workspace.js`. Operational drawers are implemented in `public/assets/js/workspace-operations.js`; connected profile/admissions work uses `workspace-people.js`, bounded access editors use `workspace-access.js`, paged teaching work uses `workspace-teaching.js`, room planning uses `workspace-scheduling.js`, employment/time review uses `workspace-employment.js`, student records use `workspace-students.js`, and internal holds/notes use `workspace-restrictions.js`. They share the same private AJAX transport. The legacy blue `#4a8bc2` appears as a decorative accent. Controls and text use darker blues against white and gray surfaces.

Direct visits and reloads outside Overview show a neutral loading panel while the deferred workspace scripts start. Overview stays hidden throughout that startup, and the breadcrumb changes from Workspace to the requested screen when navigation initializes. Overview visits retain their dashboard. This uses server-rendered hidden states and the existing startup path, with no inline script or browser cache of private records.

The dashboard reads institutional counts, intake by entry term, admissions statuses and approval queues from the database. Metrics are filtered by the signed-in person's permissions. There are no generated trends, sample totals, combined-currency balances or external analytics. Chart data has a table alternative. Browser tests use explicitly fictional responses and never connect to the application database.

## Workspace design and navigation

The workspace review covered the shared shell and directory, person/student records, catalog and calendar tools, reporting, admissions, registration, finance, HR, scheduling, communications, access and integration screens. The visual update keeps the blue, white and gray brand, with darker blue for readable text and controls. Larger labels, consistent spacing, quieter card shadows and wider record drawers improve readability across the shared screens. The full-screen report and degree-audit builders retain their task-specific layouts.

| Area | Interaction |
| --- | --- |
| Main navigation | One active parent workspace, a scrollable navigation list and persistent branding. Related screens retain their parent selection and show a breadcrumb back to it. |
| Directory navigation | Related-screen links occupy their own navigation area. Setup tools occupy a separate action group. |
| Academic catalog | Curriculum, Academic calendar and Course offerings dropdowns group related tools instead of mixing a long row of setup buttons with navigation links. |
| Reports | Report Studio is the primary action. Report requests collect request creation, personal requests and the authorized team queue. |
| Person and student records | Common tasks remain visible; secondary account, history and administrative actions use a labeled More menu. Program changes remain prominent. |
| Student account entries | An applicable credit/refund action or History remains visible. Corrections and reversal use a contextual More menu; reversal retains its separate confirmation. |
| Account menu | Initials and first name identify the trigger. Icon links provide Profile, Timetable, Bookings, Campus portal and Apply, followed by Sign out. The full name remains inside the menu. |

Keep everyday action labels short and specific, such as **Review transcript** or **Export roster page**. Keep consequential confirmation text explicit about its effect. Dropdowns reorganize existing authorized actions; opening one does not perform a mutation. Finance readers without ledger permission are not offered ledger/journal navigation, and readers without posting permission receive no hidden posting controls.

Menus use Bootstrap's keyboard behavior with native buttons and links, visible focus, expanded state and named triggers. Escape returns focus to the trigger. Opening a task from a menu records that trigger as the drawer's return point. Fixed menu positioning keeps table actions within the viewport; menu instances are disposed when their records are replaced or closed. Completing a directory request must not move focus away from a menu or editor opened while it was loading.

Phone navigation fits a 320-pixel viewport and keeps the navigation list scrollable. Record drawers use the full phone width, wide tables scroll within labeled regions, and dropdowns have bounded width and height. Validation includes keyboard navigation, drawer return focus, delayed responses, 200% text scaling, reduced motion and automated WCAG 2.2 AA-tagged checks on representative dashboard, catalog and account screens. These checks supplement manual review and do not constitute accessibility certification of the entire application.

This update uses the existing self-hosted Bootstrap and icon assets. It changes no institutional data or schema. Authorization, browser CSRF protection, private AJAX responses and POST-based sign-out remain in place.

### Choose a navigation layout

Use **Navigation layout** in the workspace header to choose a layout. The full sidebar is the default. All choices use the same server-filtered destinations and keep the existing screen, breadcrumb and record/task workflow.

- **Full sidebar** shows each icon and label in the existing scrollable sidebar.
- **Compact sidebar** gives the screen more room with an 80-pixel icon rail. Hover or focus an icon to reveal its label. The label can itself be hovered, and Escape dismisses it without moving keyboard focus. Enter follows the original link. The header's **Collapse navigation sidebar** / **Expand navigation sidebar** button switches directly between the full and compact sidebar.
- **Top navigation** replaces the side rail with **Campus**, **Operations** and **Tools** menus above the workspace. Empty permission-filtered groups are omitted. Related screens continue to mark their parent group. Bootstrap controls the menu's expanded state, arrow-key selection and Escape focus return; the shared floating-menu presentation keeps menus above clipping containers and within the viewport. Long menus scroll, labels align to the left, and text wraps. Branding, the breadcrumb and header actions remain available.

Below 992 CSS pixels, every preference uses the full labelled mobile drawer. Open it with **Open navigation**, scroll its links, or use Escape / **Close navigation** to dismiss it. The chosen desktop layout returns when the screen is wider again. Choosing a layout on a phone explicitly reports that it is saved for larger screens. Menus and flyouts are bounded at narrow sizes and enlarged text, with visible focus and the existing reduced-motion rules.

Only the layout name (`sidebar`, `compact` or `horizontal`) is saved under `etsis.workspace.navigation` in this browser and site origin. It is a presentation preference shared by users of that browser, not a person/permission preference. No record identifiers, private responses, credentials or draft contents are stored. Invalid saved values fall back to the full sidebar. When storage is unavailable the current page can still change layouts; without JavaScript the full sidebar remains the default. The preference loads before the body is rendered, so reloading another workspace does not briefly show the wrong sidebar width while the main workspace script starts.

Changing layouts does not navigate, submit a form, close a record drawer, discard a draft or grant access. Resizing an open record preview retains that preview. Actual navigation still uses the existing unsaved-work guard, private read/write APIs and server authorization. Website management, replies and newsletter links remain real external-screen links in the same filtered **Tools** group. No database migration, report, event history or new dependency is added.

Browser qualification covers all three layouts, restricted links, keyboard/hover flyouts, Bootstrap menus, current-parent state, reloads and delayed startup, storage failure, drafts/drawers, mobile transitions, 320px/200% reflow and automated accessibility. Institution-led assistive-technology acceptance remains part of release qualification.

## Application studio

The form library remembers explicit Show/Hide preferences and saved forms’ field-card, Field settings and Container settings disclosures in local storage. Collapse all / Expand all also persists. Only boolean display state and opaque form hashes are retained; names, labels, definitions, unsaved edits, answers and applicant data remain out of browser storage. Saving a new draft retains its current display choices. Display changes do not require saving the form. Clearing this site’s browser data resets display preferences; blocked storage leaves the editor usable. Automatic phone closure after selecting a form does not replace the explicit library preference.


Form administrators can create separate application schemas for each academic program. Supported field types are text, long answer, email, date, dropdown, whole number and checkbox. Fields have stable keys, labels, help text, required status, keyboard reorder controls and conditions referencing earlier fields. Conditions are validated against the schema on the server.

Draft saves use optimistic versions. Publishing requires `sis:forms:publish`, serializes on the program, and enables one immutable form revision for that program. Opening a published form creates a new draft revision. Disabling an application form stops new submissions and preserves previous submissions. Previously submitted answers are always read against the original schema.

Applicants sign in and submit for their own person; admissions staff can submit for an authorized person from its drawer. This implementation assumes sign-in is required. Submission retries use an identifier and content fingerprint, answers are encrypted through the existing message cipher, and audit records contain references rather than answers. File upload fields and anonymous applications are not implemented.

## Install and update

PHP 8.4 is the minimum. Install the locked Composer dependencies, including League CSV, with the interpreter configured for this project. Apply migration `20261106000006_CreateSisWorkspaceTables` after the earlier SIS/access migrations. It creates form schemas, program bindings, encrypted submissions and saved rules, seeds four protected permissions, and links existing accounts to person records in bounded batches. It does not import legacy institutional records. Staff restriction notes also require `20261107000001_CreateSisRestrictionNotesTable` after the campus portal migration. Resolve duplicate account-to-person links before applying it. No migration has been executed against an institutional database during this work.

Browser assets are self-hosted, with their upstream licenses copied into `public/assets/vendor`. To rebuild from the lockfile:

```sh
npm ci
npm run build:assets
```

No CDN, JavaScript build watcher, polling loop, service worker or browser storage is required. Browser mutations retain framework CSRF protection. Workspace responses are private/no-store, and private routes suppress debug collectors. PHP classes follow the Domain/Application/Infrastructure boundaries.

Workspace AJAX mutations send their typed JSON object in one URL-encoded `_workspace_json` form field. The installed router eagerly constructs a legacy input handler before application middleware; that handler accepts strings/arrays/null and throws on numeric or boolean JSON scalars. The form envelope passes that handler safely. `WorkspaceJsonBodyMiddleware` restores the original typed object before firewall inspection, CSRF validation and controller handling. The CSRF header is unchanged. The decoded JSON is limited to 2 MB with bounded nesting, and mixed/malformed envelopes are rejected. Ordinary forms keep their existing behavior. Raw JSON decoding remains available to PSR requests, but direct HTTP JSON clients with numeric/boolean values still require an upstream legacy-parser fix. No vendor code is modified by this compatibility transport.

## Validation and resource use

The PHP suite exercises foundation, portal and staff workflows with in-memory fixtures. New integration checks exercise immutable form publication, conditional validation, encrypted and repeatable submissions, import previews and content changes, canonical person linkage, permission-filtered workspace data, cursor search and bound rule queries. Schema definitions compile for MySQL, PostgreSQL, SQLite, SQL Server and Oracle; live database execution has only been checked with SQLite fixtures.

The browser check renders the real templates and assets against fictional API responses. It checks desktop/mobile layouts, the person drawer, form preview, import mapping, rule initialization, narrow-screen overflow and automated WCAG checks. These checks supplement manual accessibility review; they do not certify every screen or assistive-technology combination.

Run checks sequentially with low scheduling priority. Substitute the PHP interpreter configured in your IDE:

```sh
nice -n 15 /usr/local/bin/php84 -d memory_limit=192M vendor/bin/phpunit --configuration phpunit.xml
nice -n 15 /usr/local/bin/php84 -d memory_limit=256M vendor/bin/phpstan analyse --debug --no-progress --level=8 --memory-limit=256M src/Domain
# Run the same analysis separately for src/Application and src/Infrastructure.
nice -n 15 /usr/local/bin/php84 -d memory_limit=192M vendor/bin/phpcs --standard=phpcs.xml
ETSIS_TEST_PHP=/usr/local/bin/php84 nice -n 15 node --max-old-space-size=192 node_modules/@playwright/test/cli.js test --workers=1
```

The browser configuration uses one worker, no video or trace recording, and reduced motion. Its local fixture server exits when the check ends. Chromium must already be installed for Playwright; the test command does not download it.

Catalog edits use a locked record and a revision fingerprint to reject stale saves. Section capacity cannot fall below active enrollment. Section course/term identity stays fixed after creation. Course edits preserve the recorded course code, title and credits on existing academic credits; section fee changes leave posted charges intact. Term date changes affect subsequent eligibility and drop/withdrawal decisions, so staff should review their academic calendar before saving. Prerequisite removal changes future registration eligibility.

Final grades and assignment scores retain the domain's optimistic versions. Attendance is restricted to the term dates. A faculty assignment authorizes only the assigned section. A registration-management grant permits roster work but does not itself expose final grades or authorize score writes. Roster/context feeds load 50 rows at a time and offer further pages. The teaching directory filters by the authenticated account before reading records. Financial account lists resolve the current institutional ID and person name instead of making staff identify an account by its internal key.

Billing rules are immutable: retire a rule and create a replacement for a changed amount. Campaign content is encrypted at rest. Draft edits check the expected version and stop after queueing. Queueing does not send mail. ## Curriculum reports and student follow-through

**Reports → Open Report Studio → Start from a template** now includes **Current component ownership**, **Selected student curriculum** and **Students by major and department**. Current catalog labels require catalog authority; selected labels come from exact retained publications under student-read authority. Detail rows represent components, while the headcount starter uses distinct students. Include student/pursuit references in a saved live detail report to open the exact selection workflow and return to refreshed report results. ## Correct registered credits from enrollment load

Staff with student-read, registration management and the independent **registered-credit correction** duty can open **Student programs → Enrollment load**, choose the term and select **Registered credits · course**. The editor preserves institutional-evidence drafts through review/history/reload and confirms against exact recorded source versions. Current load changes; original registration quantity, awarded units/grade/GPA, charges and earlier load determinations remain separate. Students/advisors see current totals without correction controls or staff routing. [Workflow, authority, retained history and limits](registered-credit-corrections.md).
