# Published program details

A program has one working definition and explicitly published catalog revisions for existing academic years. Each publication retains its code, title, plain-text description, department, academic level, offered degree/award, specialization choices and selection policy. Later draft edits and reference-library renames do not replace those facts.

The [degree-audit builder](degree-audit-builder.md) separately publishes course/group requirements and policies. Program publication is not a graduation decision and does not automatically assign or replace a student's degree-audit requirements.

## Staff workflow

1. Set up [term types and academic years](academic-calendar-setup.md). Terms identify the academic year of matriculation; there is no separate catalog-year entry form.
2. Open **Academic catalog → Programs → a program → Program details & publications**.
3. Edit the code, title and description together. Choose the department, academic level and award from searchable libraries. Add a degree or certificate directly from the award chooser, or use **Degrees & awards** in the catalog toolbar.
4. Save once. Unsaved text and classification choices survive returning from a chooser or publication history. Publication stays disabled while changes are unsaved. Codes allow up to 80 letters/digits/dots/underscores/hyphens, titles up to 191 characters and plain-text descriptions up to 10,000 characters.
5. Choose **Publish for an academic year**, enter a reason and choose an existing academic year. Searches accept a blank value and use bounded pages. Choosing a year preserves the reason.
6. Choose **Review program publication**. Inspect the year, proposed catalog revision, program text, classifications and specialization choices/policy. **Revise program publication** preserves the year/reason; **Refresh program review** prepares a fresh review. An unconfirmed review expires after 20 minutes.
7. Choose **Confirm program publication**. Confirmation records the actual acceptance time and selects the next program catalog revision for that academic year.

For example, publish a B.A. definition for **2022-2023**, then a revised definition for **2024-2025**. A student's existing 2022-2023 assignment keeps its reference. New assignments entering 2024-2025 use that year's published revision. Editing today's draft without publishing for 2022-2023 does not change the labels used by a new assignment entering that older cohort.

Publishing another revision for the same year changes the default for subsequent assignments into that year. It does not move existing students. Retrying an earlier accepted confirmation returns its original receipt after later publications, edits or expiry, without restoring the earlier default.

## Program specialization setup

Open **Academic catalog → Programs → a program → Program details & publications → Program specializations**. Add a code, title, optional plain-text description and active status. Codes are unique within that program; another program may use the same code for its own specialization. Editing requires the saved revision, so another person's changes cannot be overwritten by an older form. Deactivate an unavailable specialization instead of deleting its reference.

Search and twenty-record pages stay within the selected program. Descriptions load only when opening an editor. Returning to program details preserves the unsaved parent-program text and classification choices. A rejected save leaves specialization entries on screen for correction. Names and descriptions are escaped, including literal markup.

This is **authoring/reference setup**. Creating, editing or deactivating a library entry changes no existing program publication, student pursuit, selected requirement, grade, award or financial fact. The next program publication captures the active specialization choices and their exact code, title and description. Later reference edits cannot rename or remove those retained choices. Staff can now record [student specialization choices](student-program-assignments.md#specialization-choices-within-a-pursuit) against the exact retained program revision. The [specialization requirements builder](degree-audit-builder.md#specialization-requirements) now composes independent course groups for an academic year and retains the offered choice through this publication. Staff can also [assign exact specialization requirements](student-program-assignments.md#assign-published-specialization-requirements) matching the pursuit’s retained program publication. Combined degree/specialization sharing, exclusions and evaluation remain subsequent work.

Choose **Specialization selection policy** from the specialization library. The institution sets a maximum permitted per pursuit and a default maximum; both initially equal **one**. A program inherits that default or sets its own maximum within the institutional ceiling. Its required count initially equals **zero**, meaning selection is optional. A program maximum of zero disables specialization selection, and its required count cannot exceed its effective maximum. The number of offered choices is separate from the number a student may select. Do not infer selection rules or multiple degrees from an undergraduate/graduate label.

For example, an institution can allow up to three choices, default programs to one, and let an undergraduate program explicitly allow two while a graduate program inherits one. A required count of one makes selection mandatory for that program. Saving incomplete setup is allowed, but publication requires at least that many active offered choices. Publication currently supports at most 100 offered choices and a 48 KiB definition; a size warning asks staff to shorten descriptions when needed.

Changing institutional boundaries requires the independent **`sis:catalog:policy`** permission. Catalog management alone does not grant it. The institutional form is hidden without that authority; super administrators can use it and delegate it explicitly. Program settings require `sis:catalog:manage`. Lowering a boundary never silently clamps program settings or rewrites earlier publications: an incompatible draft shows an actionable warning and must be corrected before publication.

Use the existing **Review program publication → Confirm program publication** workflow to publish the choices and policy together. The review and curated history show captured limits and offered definitions, with twenty-choice pages for long lists. Confirmation rejects changed settings or choices, including edits subsequently reverted to their old values. An already accepted confirmation still returns its original result after later policy changes. No separate specialization approval screen is needed.

For example, Lesley's [2026–2027 graduation policy](https://lesley.smartcatalogiq.com/en/2026-2027-ac-catalog-and-student-handbook/2026-2027-academic-catalog/academic-policies-procedures-and-university-services/degree-eligibility-and-graduation-information) distinguishes several undergraduate majors from earning several degrees. Its [graduate counseling catalog](https://lesley.smartcatalogiq.com/en/2026-2027-ac-catalog-and-student-handbook/2026-2027-academic-catalog/programs-of-study/mental-health-and-well-being/graduate-programs/department-of-counseling-and-psychology) lists a general clinical mental health counseling program and named specialization pathways. These examples support program-specific modeling; they do not establish a university-wide ban on multiple graduate specializations. Its [course-sharing policy](https://lesley.smartcatalogiq.com/en/2026-2027-ac-catalog-and-student-handbook/2026-2027-academic-catalog/academic-policies-procedures-and-university-services/course-information) also distinguishes institutional divisions and program exceptions. etSIS does not import those rules as universal defaults.

`20261113000001_CreateSisProgramSpecializations` adds the ULID-keyed **`sis_program_specializations`** reference table, a program/code uniqueness constraint and program-leading page index. The schema compiles for the framework's five supported database dialects. It was applied to the configured application database after bounded inspection; before/after checks confirmed existing program, event, stream-head and receipt rows were unchanged. No data conversion or new event table was needed.

The three endpoints under `/sis/programs/{program}/specializations/` are POST `page/`, POST `save/` and GET `{specialization}/`. They require current `sis:catalog:manage`; student, registration or faculty authority does not imply catalog maintenance. Saves hold the parent program lock, recheck actor/permission, enforce parent ownership and commit the reference revision with the required metadata audit. Browser mutations preserve CSRF; responses are private/no-store with debug suppression. Policy settings use GET/POST `policy/` under the same program path; institutional settings use POST `/sis/catalog/specialization-policy/`. Program policy writes lock the institutional policy before the program, check revisions/current authority and commit with metadata audit. There is no delete route or browser storage.

## History and read models

Publication creates a `sis_program_catalogs` reference, a normalized `sis_program_catalog_details` projection and a verified `sis_program_specialization_contexts` projection for the same reference. The latter retains the exact choices, institutional/program policy revisions and effective limits. It is reconstructible from protected publication events; it is not another event store. A missing or mismatched retained context stops consequential reads rather than borrowing current settings. The existing term → academic year → current program catalog selection drives subsequent matriculation/additional-program assignments. Existing students keep their `sis_student_catalogs` bindings.

Before a new entry decision confirms, an internal reader verifies the selected year's protected publication chain and retained projection. A missing/conflicting reference stops the decision rather than borrowing today's definition or treating a missing projection as an unrecorded program. Replay consumes verified pages and retains only the aggregate head and relevant year's latest publication. Admissions/registrar commands keep their existing permissions; students do not need catalog-management authority to use a published definition.

Ordinary draft views, student assignment lists and reports use indexed read models without replay or write locks. Assignment labels use retained catalog labels when a program definition was recorded. Report Studio's **Student programs & catalog cohorts** dataset adds published program code/title/description/year, department, academic level and award fields. Joins preserve one row per assignment. Earlier unversioned references have null published-detail fields; today's library does not supply inferred historical classifications.

**Published program details** shows curated definitions, academic years, revisions and accepted/recorded times in frozen 20-entry pages. It omits actors, protected reasons and raw envelopes. Earlier prepared transcript documents, academic records and financial postings are unchanged.

## Security and storage

`ProgramDefinitionWasPublished` uses the existing protected journal, with program-owned streams, expected positions and predecessor checks. There is one current `ProgramDefinition` and `ProgramClassifications`, with no numbered wrappers or parallel journal. Award/academic-level labels do not grant permissions, award a credential or infer a grading scale.

Encrypted reviews bind purpose, reviewer, operation, complete definition, academic year, proposed revision, previous reference, stream position, reason and expiry. Confirmation locks institutional policy, program, academic year and assigned classification references in that order, compares the reviewed facts and rechecks authority after waiting/replay. Stale, competing, wrong-actor, changed-reference and expired reviews cannot publish. Accepted retries verify history and return their original result without repairing projections.

The event, cohort revision, retained definition/specialization context, current-year pointer, durable receipt and required audit commit or roll back together. Draft saves use authorized CRUD, optimistic revisions and required audit. Retired classifications cannot be newly assigned; existing retired choices can remain. Awards cannot be used as departments or academic levels.

Five endpoints require `sis:catalog:manage`: GET/POST `/sis/programs/{id}/details/` and POST `/sis/programs/{id}/publication/review/`, `commit/`, `page/`. Browser mutations retain framework CSRF protection; responses are private/no-store and debug collectors are suppressed. Unsaved state remains only in page memory.

## Migration and scope

**`20261110000005_CreateSisProgramDefinitions`** adds two ULID-keyed draft/reference tables through the portable schema API. All 111 SIS table definitions compile for the framework's five supported databases. The migration was applied to the configured DDEV application database. A count-only preflight found no existing program cohort references or program-publication events. No existing event or student assignment was converted, removed or fabricated.

Older unversioned curriculum references remain unversioned; this workflow does not invent their historical approvals. Existing reference initialization remains available for programs without a recorded publication for that year. Once a year's program publication exists, new entry decisions verify and use it.

**`20261113000002_CreateSisSpecializationPolicies`** adds ULID-keyed policy and retained-context tables, seeds the optional/default-one institutional policy, and defines the protected standalone policy permission without changing role or user grants. It was applied after bounded inspection of the configured application database; before/after comparisons confirmed existing program, event, stream-head, receipt and access-assignment rows were unchanged. Both new tables compile for the framework's five database dialects. Inspection found no recorded program-publication streams, so the current alpha program-publication contract was extended directly; no compatibility wrapper, invented history or parallel event table was added. Earlier unconfirmed reviews must be refreshed. Earlier unversioned references remain explicitly unversioned.

Schools, majors/minors, specialization requirement-version selection/combined exclusions, CIP/location classifications, effective retirement and public program-discovery presentation remain later stages. Program specialization reference setup and publication policy are available above. Degree-audit selections keep their own retained requirements; evaluation and graduation remain separate work.

Fictional checks cover year-specific student labels/bindings, report joins, retained history, stale/expired/competing reviews, reference changes, permission rechecks, rollback, exact retries, frozen pages and framework replay. Actual-provider/router checks cover CSRF, private responses, permission boundaries and curated history. Browser checks cover combined editing, draft preservation, year/reason review, keyboard confirmation, narrow-screen accessibility and literal rendering.

New degree-requirement publications now retain the reviewed program revision; see [the linked publication workflow](degree-program-publication-link.md). Earlier requirements remain unlinked.

## Optional description assistance

The details editor offers [consent-based program description assistance](optional-authoring-assistance.md#academic-program-descriptions) using the institution's configured provider. Authorized authors can generate, rewrite or expand saved descriptions, inspect suggestions and copy them into the unchanged editor. Assistance never saves or publishes automatically. Normal revision checks and academic-year publication preserve earlier student references.
