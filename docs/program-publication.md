# Published program details

A program has one working definition and explicitly published catalog revisions for existing academic years. Each publication retains its code, title, plain-text description, department, academic level, offered degree/award, optional school/college, field of study and campus/site, specialization choices and selection policy. Later draft edits and reference-library renames do not replace those facts.

The [degree-audit builder](degree-audit-builder.md) separately publishes course/group requirements and policies. Program publication is not a graduation decision and does not automatically assign or replace a student's degree-audit requirements.

## Staff workflow

1. Set up [term types and academic years](academic-calendar-setup.md). Terms identify the academic year of matriculation; there is no separate catalog-year entry form.
2. Open **Academic catalog → Programs → a program → Program details & publications**.
3. Edit the code, title and description together. Choose the department, academic level, award, optional school/college, field of study and campus/site from searchable libraries. Add a degree or certificate directly from the award chooser, or use **Degrees & awards** in the catalog toolbar.
4. Save once. Unsaved text and classification choices survive returning from a chooser or publication history. Publication stays disabled while changes are unsaved. Codes allow up to 80 letters/digits/dots/underscores/hyphens, titles up to 191 characters and plain-text descriptions up to 10,000 characters.
5. Choose **Publish for an academic year**, enter a reason and choose an existing academic year. Searches accept a blank value and use bounded pages. Choosing a year preserves the reason.
6. Choose **Review program publication**. Inspect the year, proposed catalog revision, program text, classifications and specialization choices/policy. **Revise program publication** preserves the year/reason; **Refresh program review** prepares a fresh review. An unconfirmed review expires after 20 minutes.
7. Choose **Confirm program publication**. Confirmation records the actual acceptance time and selects the next program catalog revision for that academic year.

For example, publish a B.A. definition for **2022-2023**, then a revised definition for **2024-2025**. A student's existing 2022-2023 assignment keeps its reference. New assignments entering 2024-2025 use that year's published revision. Editing today's draft without publishing for 2022-2023 does not change the labels used by a new assignment entering that older cohort.

Publishing another revision for the same year changes the default for subsequent assignments into that year. It does not move existing students. Retrying an earlier accepted confirmation returns its original receipt after later publications, edits or expiry, without restoring the earlier default.

An existing student's exceptional curriculum change uses the registrar's [reviewed cohort workflow](student-program-assignments.md#review-a-cohort-change). Publication never initiates that change. The decision preserves both references in the student's existing pursuit stream; selected degree and specialization requirements require their own deliberate review.

## Schools, colleges and fields of study

Open **Academic catalog → Curriculum → Schools & fields** to maintain the two optional reference libraries. A school may be called a school, college or faculty by the institution. A field of study is an institution-managed program classification: for example, a CIP or ISCED code and its title. No national code list is seeded, fetched, inferred from the program code or asserted to be officially valid. Staff enter the code and label the institution has selected.

Both libraries reuse the existing classification editor: codes up to 40 characters, names up to 191, searchable fifty-record pages, optimistic edits and retirement instead of deletion. Codes can contain dots, slashes, underscores and hyphens. Schools/colleges can now be assigned explicitly to departments using the workflow below. Fields of study remain independent classifications. These relationships grant no permissions and do not establish grading scales or degree requirements.

Choose **School/college** and **Field of study** in **Program details** alongside the existing text and classifications. Pickers preserve all unsaved choices and program text, and can add a reference without leaving the workflow. Clear a choice to leave it unspecified. A retired reference may remain on a program that already uses it, but cannot be newly assigned. Save the draft once, then use the existing academic-year publication review. Any changed code, title, selection or classification label makes an earlier unconfirmed review stale. Earlier accepted retries keep their original result.

New publications retain each selected reference's identity, code and title, including explicit blank choices. Later library renames, retirements or draft edits cannot relabel an existing student's selected cohort. Earlier genuine publications that did not capture these fields retain that exact absence and show **Not recorded in this publication**; no current reference is substituted. A retained projection carries whether these two fields were captured, and verification rejects inconsistent or invented values. The current domain model reads both known and unrecorded historical facts without numbered model wrappers or rewritten events.

Report Studio's **Student programs & catalog cohorts** dataset includes the retained school/college and field-of-study codes/names, plus **Program school and field of study recorded**. It reuses the existing single publication join: a student keeps the classifications of the program publication selected for that pursuit, and reports do not replay streams or join today's library. A missing publication remains missing; a false recorded flag identifies an earlier publication without these captured fields. Student-record/report permissions still apply.

Migration `20261119000008_AddSisProgramClassifications` adds two nullable draft references with foreign keys, their retained publication labels and the recorded/unknown indicator. It creates no reference entries, roles, grants, event types, journal or historical backfill. SQLite uses nullable inline foreign keys without rebuilding the draft table; the other framework database engines use schema alterations. Isolated tests verify SQLite constraints and retained facts, compile changes for MySQL, PostgreSQL, SQL Server and Oracle, and cover stale reviews, retirement, private/CSRF route boundaries, literal text, historical reports and accessible mobile workflows. The development database contained one existing program draft and no retained program publications before the upgrade. The native MariaDB migration preserved that draft’s original-field digest and all twenty historical events; event, stream-head and operation-table checksums were unchanged. Both new draft foreign keys were verified afterward.

## Departments and curriculum ownership

A broad program such as `ARTS-UG` can have **School/college = College of Arts & Sciences** and no program department. Keep actual discipline departments such as English, History and Philosophy. A department can serve undergraduate and graduate study; academic level and award remain properties of each program.

**Set up the organization.** In **Academic catalog → Curriculum → Schools & fields**, create the school's reference. Open **Departments & levels**, add or edit a department, and choose **Choose department school/college**. Select the school, return to the preserved department draft and **Save classification**. **Clear department school/college** explicitly removes the current affiliation. A department has at most one current school/college; many departments can share it. Retire unavailable references instead of deleting them. Newly selecting a retired school is rejected; an existing unchanged affiliation can remain.

**Assign a component's owner.** Open **Programs → a program → Program details & publications → Majors, minors & specializations → Add a curriculum component** or edit an existing component. Select its type, enter its code/title and choose **Choose responsible department**. The department chooser shows its school/college. Returning preserves your component fields, active flag and original saved revision. **Clear responsible department** explicitly leaves the component unassigned. Save the component, then review and publish the program for the applicable academic year. Existing retired department references may remain; new selections require an active department.

For example, an `ARTS-UG` program can offer an English major owned by English and a History minor owned by History, both affiliated with Arts & Sciences. This does not require assigning either department to the whole broad program. The program's own school/department choices stay independent: component ownership does not silently fill them, restrict eligibility or grant departmental access. Cross-college offerings remain possible. Joint component ownership is supported below. Joint ownership of an entire program and deeper organizational hierarchies remain separate extensions.

**Retain the reviewed organization.** A new program publication captures each offered component's selected department and that department's school/college, including their exact labels. A deliberately unassigned department or school is retained as unassigned. Earlier publications without a department field display **Not recorded in this publication**; today's references never fill that gap. Renaming, retiring or moving a department affects current setup and future reviewed publications. It does not relabel accepted program/component requirements, student choices or their assigned curriculum. A changed ownership source invalidates an unconfirmed program review; retrying an accepted confirmation returns its original result.

**Inspect a student's curriculum.** The existing [student component selection/history](student-program-assignments.md#specialization-choices-within-a-pursuit), assigned requirements and [combined progress](student-degree-progress.md#combined-curriculum-progress) resolve the retained program publication. Staff can see the responsible department when choosing and inspecting components. Students see retained department and school labels on their private combined progress cards. The student response contains organization codes/titles without internal organization identifiers. These labels do not alter course placement, sharing, earned credits, GPA or graduation authority. Use [curriculum reporting](curriculum-reporting.md) for current component ownership and exact retained student component/department labels, with separate permissions and explicit headcount grain.

Catalog setup requires `sis:catalog:manage`, saved revisions and required audits. Reference saves and new program publications recheck sources and authority at completion; a failure rolls back the operation. Apply `20261121000011_AddSisAcademicOrganization` before using these editors. It adds nullable school/department references to the existing classification/component tables, grants no access and guesses no affiliation for existing rows. Reference setup remains audited CRUD; historical organization labels live in the existing protected publication journal, with bounded paging and earlier unknowns preserved.

### Joint department ownership

A component may have one optional **Responsible department** and up to five **Additional responsible departments**. For example, an interdisciplinary Linguistics major within `ARTS-UG` can have English as its primary owner and Linguistics and Anthropology as joint owners. Each department retains its own school/college, including when those colleges differ. These choices do not assign an administrative department to `ARTS-UG` or create additional majors, degrees or eligibility rules.

1. Open the existing curriculum component editor using the path above. Choose the primary responsible department if applicable.
2. Under **Additional responsible departments**, use **Add responsible department**. The shared library shows department codes, names and colleges; search or page to choose one. **Back to curriculum component** returns without changing the choices. Unsaved component fields, required-major relationship and saved revision remain intact.
3. Add further owners, or use **Remove department …** to remove one. A department cannot appear twice or repeat the primary owner. Choosing an additional owner as primary removes it from the additional list and explains the change; the former primary is not automatically added elsewhere. The add action becomes unavailable at five additional owners. Removing an owner makes room again.
4. Use **Save curriculum component**. A rejected save retains the draft for correction or retry. Existing retired owners may remain or move between primary and additional positions; a retired department cannot be newly assigned after removal.
5. Review and publish the program for the applicable academic year. The review includes the exact primary owner, all additional owners and each owner's college. Membership, department-label or college changes invalidate an unconfirmed review. An already accepted confirmation still returns its original receipt.

New program publications explicitly retain `additional_departments`, including an empty list when no additional owner was selected. Earlier publications without that field remain **Not recorded in this publication**. Current choices never fill an earlier gap. Student selection, assigned component inspection and staff/private student combined progress resolve the exact assigned publication, so later reference edits preserve the original ownership labels. Student responses contain organization codes and names without organization identifiers. Academic allocation, credit, GPA and sharing calculations are unchanged.

Apply `20261123000005_CreateSisComponentDepartments`. Its ULID-keyed relationship table stores current draft membership with foreign keys and a unique component/department pair. It creates no inferred memberships, grants, historical events or reporting fields. Current edits remain audited CRUD; publications and receipts use the existing protected history. The existing component `save/` request accepts the complete `additional_department_ids` list, bounded to five distinct departments. Catalog authority, CSRF, private/no-store responses, saved-revision checks, ordered source locking and final source/actor/audit verification apply throughout. Ownership alone does not permit a department to access student records. This adds no department co-ownership reports. Whole-program ownership is configured separately below.

## Whole-program joint department ownership

Open **Academic catalog → Curriculum → Programs → program record → Program details & publications**. Use **Choose department** for the optional primary responsible department. Under **Program department ownership**, choose **Add responsible department** for up to five additional departments. The searchable shared library offers **Back to program details**, preserving unsaved text and other classifications. Remove a department explicitly with its labelled button; choosing an additional department as primary removes it from the additional list. Save before reviewing publication. A failed save preserves your entries.

For example, an interdisciplinary `ARTS-UG` program may have English as primary and History and Linguistics as joint owners. Each department keeps its own college. The program's separate **School/college** classification describes program administration and is neither populated nor changed by these selections. A broad program can leave its primary department blank and still select joint departments. Program owners do not automatically become owners of its English major, History minor or other components; configure those separately. Ownership grants no access, curriculum eligibility, extra credentials or course credit.

Existing retired departments may remain or move between primary and additional responsibility. Once removed, they cannot be newly assigned while retired. Duplicate departments, the primary repeated as additional, nondepartment references and more than five joint owners are rejected atomically. Save rechecks the displayed revision, current signed-in catalog authority, department/college sources and required audit. Existing memberships retain their identities when only input order changes.

New reviewed publications retain the primary department's own college and every additional department's complete code/title/college definition in the existing program publication event. Renaming or moving any selected department/college invalidates an unaccepted review. Accepted retries return their original receipt. Later edits and publications cannot relabel an earlier student's assigned curriculum. Earlier publications lacking these ownership fields remain unknown; a new empty list means **none**, and an explicit null college means **not assigned**. Staff program history and retained requirements use those exact definitions.

Apply `20261123000006_CreateSisProgramDepartments`. `sis_program_departments` stores current ULID-keyed draft memberships with foreign keys and a unique program/department pair. `sis_program_catalog_ownership` is an immutable, reconstructible projection of the existing protected publication, tied to its identifier, program, stream version and canonical snapshot hash. The new `department_ownership_recorded` flag defaults to zero for earlier publications. A known publication missing its projection is rejected, rather than being relabelled unknown. The migration infers no earlier ownership, rewrites no academic facts and refuses destructive rollback. Full-replacement program-detail POSTs must explicitly provide `additional_department_ids`, including `[]` to clear them; CSRF and private/no-store boundaries remain.

Assigned staff/single-component and private student degree progress show these retained owners alongside independent component ownership. Older frozen reviews retain their original context and reproduction hash. Existing reporting fields, eligibility, calculations and grants are unchanged.

## Program campuses and sites

Program locations use the same **Campuses & sites** library as course sections. Set up a definition from **Academic catalog → Curriculum → Campuses & sites**, or add one from **Program details → Choose primary campus/site**. Choose an active entry, save all program details together, and publish through the existing academic-year review. Clearing the choice records an explicit blank in the next publication. Retire references instead of deleting them; an already assigned retired campus can remain, but it cannot be newly selected after clearing.

A program campus is optional descriptive context. It does not reserve a room, constrain admissions or registration, establish delivery mode, or automatically select the campus on its course sections. Online programs can leave it blank. Programs can also record additional offering sites in the same editor. Individual sections retain their own campus/site independently. These program affiliations do not determine a student's personal location or authorize teaching in a room; location-based eligibility policies remain separate work.

For example, publish a program under **Main Campus** for 2024–2025 and matriculate a student under that revision. Rename the reference to **North Campus**, clear the draft location for an online program, or publish a later revision: that student's assigned definition still says **Main Campus**. The original publication/event and accepted retry receipt remain unchanged. New publications retain the deliberately reviewed location rather than looking it up when reading student history.

Earlier publications without a campus key still show **Not recorded in this publication**. New publications with a deliberate blank show **Not specified**. `ProgramClassifications` keeps both meanings in one current model. The retained campus ID/code/title and `campus_recorded` marker are verified against protected publication facts; a known/unknown mismatch or incomplete snapshot is rejected. No current classification is substituted for an earlier unknown.

### Additional offering sites

The same **Program details** form now has an optional **Primary campus/site** and an **Additional offering sites** section. Select **Add offering site** to use the shared searchable campus library. Choose up to twenty additional sites; duplicates and repetition of the primary campus are rejected. Names and codes stay visible beside concise Remove buttons. Choosers preserve unsaved program text. Choosing an additional site as the primary campus moves it out of the additional list, with an explanation; the previous primary is not automatically added elsewhere.

Save the complete draft once, then review and publish the exact locations for an academic year. An already assigned retired site can remain until deliberately removed, but cannot be newly selected afterward. A newly selected reference that changes or retires during the save aborts the whole transaction. Drafts and reference setup remain audited CRUD; the existing program publication event retains the complete reviewed site snapshots with its other academic definitions. There is no independent site publication or extra recovery process.

Earlier publications without `additional_campuses` remain **Not recorded in this publication**, even if they recorded a single campus. A newly reviewed empty list means **No additional sites**. Retained rows use a separate recorded marker to preserve this distinction. Later additions, removals, renames and publications do not change a student's existing program/cohort references. A changed review, missing known site snapshot or final audit/authority/expiry failure cannot produce a partial publication. Accepted retries return the original result and never reapply an older draft selection.

### Campus reporting

Open **Report Studio → Start from a template → Program campuses**, or choose **Student programs & catalog cohorts** and select fields yourself. The template compares the **Published program campus/site name** retained for the student's selected cohort with the **Current program campus/site name** in today's draft/reference setup. Include **Program campus/site recorded** to distinguish an earlier unknown from a deliberate blank. Published and current codes are also available for typed filters, grouping and joins.

The source retains **one row per program pursuit**, including earlier/closed pursuits when selected by report filters. Count distinct student identities for a headcount. The new joins are single-record lookups; they do not multiply pursuit rows, replay history, or acquire academic write locks. A later publication does not move an existing student's cohort binding. Existing preview/save/live/static/share/export controls and report/student-data permissions apply. No private publication reasons, student answer bodies or raw events enter the source.

**Program offering sites** starts with every current program, including programs with no extra sites, and requires catalog-management data permission. Its additional-site join adds one row per affiliation; count distinct program references for totals. It contains no student identities and needs no student-data grant.

**Cohort program sites** uses the student's assigned program publication and requires student-read authority. Its left join adds one row per pursuit and retained additional site, preserving empty or unknown lists. Include **Additional program sites recorded** to distinguish an earlier unknown list from a known empty list; a missing program definition remains unknown separately. Count distinct students for a headcount. These are program offering locations, not evidence that a particular student attended a site. The original **Program campuses** template still compares the single primary/contextual campus without adding the many-site join.

Both sources reuse the existing visual builder, filters, summaries, encrypted dynamic saves/sharing, static captures and exports. A shared definition grants no additional source permissions. Current reference changes affect dynamic current-site reports; captured results and cohort-bound site snapshots retain their original labels. Reports use indexed projection joins and read no raw event payloads.

## Program specialization setup

Open **Academic catalog → Programs → a program → Program details & publications → Majors, minors & specializations**. Add a code, title, optional plain-text description and active status. Codes are unique within that program; another program may use the same code for its own specialization. Editing requires the saved revision, so another person's changes cannot be overwritten by an older form. Deactivate an unavailable specialization instead of deleting its reference.

Search and twenty-record pages stay within the selected program. Descriptions load only when opening an editor. Returning to program details preserves the unsaved parent-program text and classification choices. A rejected save leaves specialization entries on screen for correction. Names and descriptions are escaped, including literal markup.

This is **authoring/reference setup**. Creating, editing or deactivating a library entry changes no existing program publication, student pursuit, selected requirement, grade, award or financial fact. The next program publication captures the active specialization choices and their exact code, title and description. Later reference edits cannot rename or remove those retained choices. Staff can now record [student specialization choices](student-program-assignments.md#specialization-choices-within-a-pursuit) against the exact retained program revision. The [specialization requirements builder](degree-audit-builder.md#specialization-requirements) now composes independent course groups for an academic year and retains the offered choice through this publication. Staff can also [assign exact specialization requirements](student-program-assignments.md#assign-published-specialization-requirements) matching the pursuit’s retained program publication. The [combined curriculum review](student-degree-progress.md#combined-curriculum-progress) now uses the retained sharing rule; [incompatible curriculum choices](#incompatible-curriculum-choices) are implemented below; remaining evaluation/award rules stay open.

Choose **Specialization selection policy** from the specialization library. The institution sets a maximum permitted per pursuit and a default maximum; both initially equal **one**. A program inherits that default or sets its own maximum within the institutional ceiling. Its required count initially equals **zero**, meaning selection is optional. A program maximum of zero disables specialization selection, and its required count cannot exceed its effective maximum. The number of offered choices is separate from the number a student may select. Do not infer selection rules or multiple degrees from an undergraduate/graduate label.

For example, an institution can allow up to three choices, default programs to one, and let an undergraduate program explicitly allow two while a graduate program inherits one. A required count of one makes selection mandatory for that program. Saving incomplete setup is allowed, but publication requires at least that many active offered choices. Publication currently supports at most 100 offered choices and a 48 KiB definition; a size warning asks staff to shorten descriptions when needed.

Changing institutional boundaries requires the independent **`sis:catalog:policy`** permission. Catalog management alone does not grant it. The institutional form is hidden without that authority; super administrators can use it and delegate it explicitly. Program settings require `sis:catalog:manage`. Lowering a boundary never silently clamps program settings or rewrites earlier publications: an incompatible draft shows an actionable warning and must be corrected before publication.

Use the existing **Review program publication → Confirm program publication** workflow to publish the choices and policy together. The review and curated history show captured limits and offered definitions, with twenty-choice pages for long lists. Confirmation rejects changed settings or choices, including edits subsequently reverted to their old values. An already accepted confirmation still returns its original result after later policy changes. No separate specialization approval screen is needed.

For example, Lesley's [2026–2027 graduation policy](https://lesley.smartcatalogiq.com/en/2026-2027-ac-catalog-and-student-handbook/2026-2027-academic-catalog/academic-policies-procedures-and-university-services/degree-eligibility-and-graduation-information) distinguishes several undergraduate majors from earning several degrees. Its [graduate counseling catalog](https://lesley.smartcatalogiq.com/en/2026-2027-ac-catalog-and-student-handbook/2026-2027-academic-catalog/programs-of-study/mental-health-and-well-being/graduate-programs/department-of-counseling-and-psychology) lists a general clinical mental health counseling program and named specialization pathways. These examples support program-specific modeling; they do not establish a university-wide ban on multiple graduate specializations. Its [course-sharing policy](https://lesley.smartcatalogiq.com/en/2026-2027-ac-catalog-and-student-handbook/2026-2027-academic-catalog/academic-policies-procedures-and-university-services/course-information) also distinguishes institutional divisions and program exceptions. etSIS does not import those rules as universal defaults.

### Course sharing between curriculum components

In **Majors, minors & specializations → Specialization selection policy**, choose **Course sharing between degree and specializations**:

- **Apply a course to one component** is the initial program setting.
- **Allow a course in degree and specialization requirements** permits intentional overlap across components.

This is independent of the one-group/multiple-group setting inside each degree or specialization requirements publication. Allowing overlap across components does not override either component's internal group policy. Requirement placements may reuse eligible work where policy permits; overall earned credits and GPA must still count each accepted contribution once. A specialization/minor label does not supply a sharing rule.

Saving uses the existing program revision, institution → program lock order, `sis:catalog:manage` authority and required audit. Publication review displays the choice and retains it in the existing protected program event and verified specialization context. Changing the setting—even changing it back—invalidates an unconfirmed review. Later edits preserve earlier publications, student bindings and accepted retry receipts. An earlier publication that lacks the field displays **Not recorded**; it never borrows today's default or editable program setting.

## History and read models

Publication creates a `sis_program_catalogs` reference, a normalized `sis_program_catalog_details` projection and a verified `sis_program_specialization_contexts` projection for the same reference. The latter retains the exact choices, institutional/program policy revisions and effective limits. It is reconstructible from protected publication events; it is not another event store. A missing or mismatched retained context stops consequential reads rather than borrowing current settings. The existing term → academic year → current program catalog selection drives subsequent matriculation/additional-program assignments. Existing students keep their `sis_student_catalogs` bindings.

Before a new entry decision confirms, an internal reader verifies the selected year's protected publication chain and retained projection. A missing/conflicting reference stops the decision rather than borrowing today's definition or treating a missing projection as an unrecorded program. Replay consumes verified pages and retains only the aggregate head and relevant year's latest publication. Admissions/registrar commands keep their existing permissions; students do not need catalog-management authority to use a published definition.

Ordinary draft views, student assignment lists and reports use indexed read models without replay or write locks. Assignment labels use retained catalog labels when a program definition was recorded. Report Studio's **Student programs & catalog cohorts** dataset adds published program code/title/description/year, department, academic level and award fields. Joins preserve one row per assignment. Earlier unversioned references have null published-detail fields; today's library does not supply inferred historical classifications.

**Published program details** shows curated definitions, academic years, revisions and accepted/recorded times in frozen 20-entry pages. It omits actors, protected reasons and raw envelopes. Earlier prepared transcript documents, academic records and financial postings are unchanged.

## Check retained publication history

Open **Academic catalog → Programs → a program → Program details & publications → Published program details**, then select **Check program publication history**. This action requires `sis:catalog:manage`, `sis:history:verify` and `sis:audit:read` together. Catalog editing alone does not grant support access.

Run the check deliberately. It compares recorded publications with retained cohort details, organizational/location snapshots, offered specialization choices and the current publication for each academic year. A newer year does not supersede an older year's own current catalog. Unpublished records report no publication observed, with earlier history unknown. Missing evidence, changed boundaries and limits require review rather than partial certification.

The drawer shows fixed outcomes/counts and private support references, without publication definitions or reasons. **Back to record** returns to the same publication page and restores focus. This check publishes or repairs nothing and does not establish student eligibility, degree completion or every dependent source's integrity. ## Majors, minors and curriculum component types

Open **Academic catalog → Programs → a program → Program details & publications → Majors, minors & specializations**. **Add a curriculum component** now includes an explicit **Curriculum component type**: major, minor, concentration, track or specialization. The initial choice for a new reference is specialization. Codes remain unique within the program, with a stable ULID and a separate retained requirements publication. A major/minor name does not create a second person, student, pursuit, degree or credential. Components in different programs remain separate definitions; reusable course groups provide shared requirement content.

**Specialization selection policy** retains the existing institutional ceiling, inherited/program maximum, overall required count and course-sharing policy. **Limits by curriculum type** optionally adds minimum/maximum counts for each type. These constraints all apply together. For example, first authorize an institutional ceiling and program maximum of at least two, then require one major (minimum one, maximum one) and allow an optional minor (minimum zero, maximum one). The default institutional ceiling remains one; the new feature does not silently increase it. Unchecked type limits add no constraint beyond the overall policy. A zero maximum for one type excludes it from student selection. Each rule uses exact whole numbers from zero through one hundred; at most five rules exist.

Save drafts, then review and confirm the program publication for the academic year. Publication retains each offered component's role and the exact type limits in the existing program publication event and projection. It rejects a missing role, too few active offered components of a required type, incompatible aggregate minima/maxima, or an overall requirement that the permitted types cannot satisfy. A draft may remain incomplete while staff prepare the curriculum; it cannot become a valid publication. Changing a role or type limit invalidates an unconfirmed publication review. Later edits or retirement preserve earlier publications, assignments and original receipts.

Registrars use the existing **Students → program pursuit → Specializations** selection workflow. Offered and recorded choices show their retained type; each checkbox has an accessible type description. The screen explains counts by constrained type, preserves selections across search/pages and disables review until the type limits are satisfied. The server independently enforces those limits before preparing a confirmation and on confirmation/replay against that pursuit's exact program publication. Selecting two minors cannot satisfy a required major. Moving to a different cohort still requires explicit cohort and selection review; today's role or policy never changes an earlier selection.

Each selected major/minor uses the existing **Requirements for …** authoring/publication/assignment workflow, approved exceptions, course routing and independent/combined degree-progress reader. Its type is descriptive curriculum scope, not a new allocation or GPA algorithm. Combined staff and owner reviews name majors/minors from retained publications and use the existing program course-sharing policy. Shared work contributes to each allowed requirement, while actual earned credit/GPA retain their existing deduplication. A missing required major blocks the owner degree-only shortcut and returns a registrar-review outcome without a partial allocation. Student responses retain only safe labels and the existing private captured detail; no internal component identities, staff reasons or raw rules are added.

Earlier published snapshots without role/type-limit keys round-trip with those fields absent. Earlier working references migrate with a null role; staff must explicitly classify every active offered reference before its next publication. Titles/codes never infer a role. A missing historical type is displayed as unrecorded and is never borrowed from the current draft. The additive migration `20261121000009_AddSisCurriculumComponentKinds` adds only nullable `kind` and bounded JSON `kind_limits` authoring fields to the existing tables. It creates no new event table, grants, academic/financial facts or historical backfill. Existing program/student streams, expected versions, expiring actor-bound reviews, original-result receipts, scope checks, CSRF, private/no-store responses and replay limits continue to apply. Required audits and final authority checks cover new authoring/policy writes.

Independent graduation/credential decisions, official transcript component presentation, exclusion exceptions beyond the incompatible pairs below, broader location eligibility and qualified larger/longer evaluations remain separate roadmap work. A major/minor selection or a feasible progress review does not confer a degree.

### Example: a broad BA program with one major and an optional minor

An institution can organize several majors under one broad academic program. For example:

| Setting | Example |
| --- | --- |
| Program code | `ARTS-UG` |
| Program title | Undergraduate Arts |
| Academic level | Undergraduate |
| Award | Bachelor of Arts |
| Offered majors | English, History, Philosophy |
| Offered minors | History, French |

The code is an institutional label. Academic level and award are separate settings; including `BA` in a code does not configure either one or automatically select a major. A subject-specific program such as `BA.ENG` can instead include the English curriculum directly in its program requirements, without requiring another English selection. Choose the structure that matches the institution's curriculum.

**1. Add the offered choices.** Open **Academic catalog → Programs → a program → Program details & publications → Majors, minors & specializations**. Add each major with type **Major** and each minor with type **Minor**. Offering three majors gives students three alternatives; it does not require them to complete all three. Codes must be unique within the program, so use different codes for a History major and History minor, such as `HIST-MAJ` and `HIST-MIN`.

**2. Configure one required major plus an optional minor.** Open **Specialization selection policy**. Some current controls still use “specializations” to mean all curriculum components, including majors and minors. A major and a minor therefore count as **two selections** toward the overall maximum.

| Control | Value for this example |
| --- | --- |
| **Institution-wide boundaries → Institution-wide maximum specializations** | At least **2**; keep a higher existing ceiling if appropriate |
| **Default maximum for programs** | May remain **1** if other programs should keep that default |
| **Use institutional default maximum** | Clear this option when the default is still 1 |
| **Program maximum specializations** | **2** |
| **Required specializations (zero means optional)** | **1** overall |
| **Limits by curriculum type → Major** | Enable; minimum **1**, maximum **1** |
| **Limits by curriculum type → Minor** | Enable; minimum **0**, maximum **1** |
| Other curriculum types | For this major/minor-only example, enable each remaining type limit with minimum **0**, maximum **0** |

The institution's ceiling and default both initially equal one. Raise the ceiling before trying to save a program maximum of two. The ceiling permits programs to use a higher maximum; it does not automatically raise every program's default. Institution-wide boundaries require the appropriate institutional authority. Unchecked type limits add no restriction beyond the overall policy, so explicitly exclude other types when only majors and minors should be selectable.

Use **Institution-wide boundaries**, shown first and expanded above **Program limits**, to change the ceiling. Choose **Save institutional specialization boundaries** before increasing the program maximum. The program field's up arrows use the **saved** ceiling; editing the institutional field alone leaves that limit unchanged. Manually typing a larger program maximum does not bypass validation. An unsaved-changes notice explains the pending institutional edit. After the institutional save succeeds, the program's arrow limit and inherited default refresh in place, preserving unsaved program counts, type limits and course-sharing choices. Then choose **Save program specialization policy** separately. The institutional panel requires `sis:catalog:policy` in addition to the catalog-management access used to open this screen.

With these settings, **English major alone** and **English major plus History minor** are valid. An empty selection or a minor alone is invalid; two majors or two minors also exceed the type limits. The overall required count is one because the minor is optional; setting it to two would require a second component. Save the settings, then review and confirm the program publication for the applicable academic year. Saving the draft alone changes no student's requirements or choices.

**3. Publish and assign the requirements.** Put shared BA requirements, such as general education and overall credit minimums, in the program's **Degree audit requirements**. Use **Requirements for …** on each major/minor to build and publish its own course requirements against the matching program publication. Reusable course groups can supply shared content.

After the student has a program pursuit with the appropriate retained program publication, use **Students → Student programs → Specializations** to [record the student's choices](student-program-assignments.md#specialization-choices-within-a-pursuit). Assign the program's degree requirements and [assign a matching requirements publication](student-program-assignments.md#assign-published-specialization-requirements) to each selected major/minor. Selecting a component does not automatically assign its requirements.

**4. Review the selected curriculum together.** For an English major with a History minor, **Combined curriculum progress** checks the shared BA requirements, English-major requirements and History-minor requirements. History-major and Philosophy-major requirements do not apply because those majors were not selected. The student's portal uses these assigned requirements for its combined progress view. Missing required choices or missing requirement assignments require registrar attention.

Choose the published [course-sharing policy](#course-sharing-between-curriculum-components) deliberately. A course may satisfy requirements in more than one component only when policy permits; a three-credit course still contributes three earned credits to the degree total. Component totals are not added together to manufacture additional earned credit. Combined progress is a current review, not an official graduation decision.

**Application and portal boundary:** applicants currently choose the academic program and entry term. Adding these offered components does not automatically add major/minor selectors to the application. Staff record the choices and assign their requirements after matriculation; students cannot yet declare or change them through the portal. Use the [department ownership setup](#departments-and-curriculum-ownership) for each component independently of the broad program. Use [required-major relationships](#required-major-relationships) to allow Creative Writing only when the English major is selected.


## Required-major relationships

A concentration, track or specialization may require **one specific major in the same program**. For example, broad program `ARTS-UG` can offer English and History majors, plus Creative Writing as a concentration requiring English. A student may choose English alone or English with Creative Writing. History with Creative Writing is rejected unless English is also selected and the program allows that many majors. An independent minor does not need a required-major link.

**Author the relationship.** Add an active **Major** component first. In the concentration, track or specialization editor, choose **Choose required major**, search this program's majors and choose **Use major …**. The chooser pages twenty references at a time and preserves the component's unsaved type, code, title, description, department and active flag. Save the component explicitly. **Clear required major** removes the working relationship. Major and minor components cannot require a major; clear a relationship before changing a linked component into either type. A new link requires an active major in the same program. The component's responsible department remains an independent choice.

**Set counts for the whole combination.** Both the major and its concentration count toward the overall maximum. For one required major and an optional concentration, set the overall required count to **1**, overall maximum to **2**, major limits to **1–1** and concentration limits to **0–1**. To permit an optional minor as well, save an institution-wide ceiling of at least **3**, set the program maximum to **3**, and set minor limits to **0–1**. For this example, set the other types to **0–0** if they should not be selectable. A required-major link alone does not require the student to choose a concentration. Multiple majors remain possible when the institution/program/type limits permit them.

**Publish the exact relationship.** Review and publish the program for the applicable academic year. Each offered child retains its required major's identity, code and title within that same publication. A retired or reclassified required major must be corrected, its children made independent, or those children retired before the next publication. Draft editing remains available for those corrections. Publication rejects combinations whose required-major links and count/type limits cannot produce a valid selection. Verification is bounded by the existing one-hundred offered-choice limit and ten thousand major-search states; exceeding verification stops publication with an explanation and leaves the draft available. It never accepts a partial verification.

**Select and inspect the student's curriculum.** The registrar uses the pursuit's retained program publication in **Student programs → Specializations**. Select the required major together with its linked component, then review and confirm. Removing only the major leaves the child checked and disables review with a missing-major message. Choose the major again or deliberately remove the linked child; search and page changes preserve both choices. The server repeats the retained relationship and count checks. Selections and requirement assignments remain separate decisions: assign the matching published requirements for each selected component before using combined progress. Staff and private student progress cards show the retained required-major label. The owner response contains its code/title without the internal major identifier.

Renaming, retiring or changing today's relationship affects future reviewed publications. It never rewrites an accepted publication, student choice or assigned requirements. Earlier publications without the relationship field remain **Not recorded in this publication**; a new explicit blank is **Required major: none**. No link is inferred from component names, departments or existing student rows. Accepted retries return their original receipt, including after later choices or expiry. An unaccepted review must still match the current reviewed source and authority.

Apply `20261121000012_AddSisComponentMajorLinks` before using the editor. It adds one nullable ULID self-reference to the existing component library, with no new journal, permissions or historical backfill. Browser saves explicitly supply `parent_major_id`, including `null` when independent; the paged component endpoint accepts an optional component-kind filter. Current authoring remains audited CRUD; retained relationships live in the existing protected program publication and student decision workflows. Joint/multiple required majors, exclusion rules beyond the incompatible pairs below, applicant choices, student declaration changes and official transcript/credential presentation remain separate work.


## Incompatible curriculum choices

Institutions can define pairs of components that cannot be selected together within one program. For example, a broad **ARTS-UG** program can offer an **English major**, **History major** and **English minor**, while disallowing the English major together with the English minor. The History major and English minor remain available together when the other limits allow them.

1. Open **Academic catalog → Programs → Program details & publications → Majors, minors & specializations → Specialization selection policy**.
2. Keep the overall and per-type limits consistent. For one major and an optional minor, use an overall minimum of **1**, maximum **2**, major limits **1–1** and minor limits **0–1**. Save a sufficiently high institutional ceiling first when necessary.
3. In **Incompatible curriculum choices**, choose **First curriculum component** and **Incompatible with**, then **Add incompatible pair**. The selectors contain the program's active offered choices. Each pair works in both directions. A pair does not imply other pairs: prohibiting A/B and B/C still permits A/C unless explicitly prohibited.
4. Add or remove pairs, then **Save program specialization policy**. Failed saves retain proposed pairs and other settings. **Remove incompatible pair** removes that draft rule explicitly. The policy supports thirty-two distinct pairs; self-pairs, duplicate/reversed pairs and references outside the active program choices are rejected. If a paired component is retired, reactivate it or explicitly remove that draft pair before saving/publishing the affected policy.
5. Review and publish the program for the academic year. The review and publication history show the exact retained pairs. Publishing verifies that at least one selection can satisfy all overall/type limits, required-major relationships and incompatible pairs together. An impossible or overly complex policy stays unpublished. Verification stops after ten thousand search nodes; it never approves a partial check.

The registrar's **Student programs → Specializations** editor uses that pursuit's retained program publication. Selecting both components leaves them checked, explains the conflicting pair and disables review until one is removed. The server repeats the check during actual review/confirmation and when verifying recorded selections. Search, paging and other independent choice rules retain their behavior. There is no automatic replacement, curriculum reassignment or exception approval.

Later policy edits or publications do not rewrite an earlier student's choices. Existing accepted retries return their original receipt and cannot replace a later selection. An earlier publication without the new field keeps that field absent; new publications explicitly record an empty or populated list. The public [program catalog](public-program-catalog.md) shows only code/title pairs from its selected publication, with no internal component identities. Its separately reviewed website version remains pinned until a publisher changes it.

These rules concern combinations of majors, minors and other curriculum components. They do not exclude academic credits, prohibit transfer credit, change course sharing or alter degree minimums. Reviewed exceptions, applicant declarations, broader location eligibility and credential decisions retain their separate workflows.

Apply **`20261123000013_AddSisComponentExclusions`** through the normal migration runner before using this policy. It adds one nullable text column to the existing operational policy table. It grants no permission, changes no recorded publication or selection and creates no new journal. Draft setup retains existing catalog authority, revisions, source rechecks and atomic audit; publications and student decisions retain their existing protected streams.


## Program offering sites and section registration

Publishing a program campus or additional offering site does not automatically restrict registration. A section can explicitly enable [the program cohort campus rule](section-publication.md#require-the-assigned-program-cohort-to-include-the-section-campus), then publish and select that offering. When enabled, its campus must appear in the student's actual assigned published program cohort. A newer program publication or current draft does not replace that assignment. A known primary or additional-campus match qualifies; incomplete earlier location evidence without a positive match requires registrar review. The rule describes program offering eligibility and does not determine the student's personal attendance campus.
